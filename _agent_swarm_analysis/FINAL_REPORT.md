# Финальный отчёт: архитектура, дефекты и рекомендации — «Метаболический контур»

**Дата:** 2026-09-13
**Оркестратор:** Claude Sonnet 5
**Метод:** рой из 4 аналитических агентов поверх уже существующих отчётов ридеров (`Docs/code_analysis/agents/reader1-4`) и вердикта по скиллам (`Docs/skills_analysis/skills_evaluation_verdict.md`). Первая попытка шла через `agy` (Gemini 3.1 Pro) — два агента (Quality, частично Logic) успели отработать до упора квоты, после чего Gemini-квота закончилась (сброс через ~2ч24м) и три агента зависли в бесконечном ретрае. Зависшие процессы были убиты, а анализ Logic (продолжен и полностью верифицирован), Consistency и Skills-Critic — переделаны заново через Sonnet-субагентов с построчной верификацией по реальному коду. Все находки ниже проверены чтением конкретных файлов, а не пересказом черновиков.

Файлы-источники: `analyst_logic_final.md`, `analyst_quality.md`, `analyst_consistency.md`, `skills_critic.md` (этот же каталог).

## 1. Как устроена система (кратко)

- **Ядро (`health_core/`, ~4200 строк):** вся арифметика детерминирована — BMR (Mifflin/Katch), адаптивный TDEE по Холлу, нижняя граница калорий (модель Альперта), макросы, 14+ гардрейлов защиты мышечной массы и безопасности, MATADOR-рефиды, симуляция прогноза (Форбс).
- **`plugin/` (~6800 строк):** 30 инструментов (схемы в `schemas.py`, реализация в `tools.py`) — LLM вызывает их, сам никогда не считает числа.
- **`bot/` (~1250 строк):** собственный агентный цикл на aiogram — **полностью заменил** описанный в SPEC.md Hermes Agent. Держит историю в SQLite, fallback-цепочку из 8 LLM-провайдеров.
- **`admin/` (~4760 строк):** веб-панель, отдельный OS-процесс (запускается как subprocess ботом).
- **`scripts/` (~950 строк):** cron-задачи (утренний чек-ин, вечерний отчёт, напоминания, бэкапы).
- **Философия:** узкий фокус на «сбросить вес, сохранив мышцы» для одного пользователя на тирзепатиде, 1 vCPU/1GB RAM, никаких тяжёлых ML-зависимостей.

Общий вывод по архитектуре: ядро спроектировано методологически грамотно (относительные, не абсолютные пороги; принцип «нет данных → гард не судит»; отказ вместо выдумывания цифр), но **документация (SPEC.md, Core/*.md) отстала от кода на порядок** — см. раздел 3.

## 2. Критические дефекты кода (по убыванию серьёзности)

### 🔴 Опасные для медицинской логики

1. **Инвертирован знак в `adaptive_tdee`** — `health_core/energy.py:201`
   `return mean_intake + (delta_weight * 7700 / window_days)` вместо `mean_intake - (...)`.
   При успешном похудении система **занижает** расчётный расход энергии и на следующем цикле режет калораж ещё сильнее — то есть чем лучше худеешь, тем жёстче тебя ограничивают. Прямой путь к урезанию ниже BMR, голоду, срывам. Числовой пример: реальный TDEE 2550 ккал, код выдаёт 1450 ккал (разница 1100 ккал).
   **Фикс:** заменить `+` на `-`.

2. **Гардрейлы LBM_RATIO/LBM_DRIFT игнорируют направление изменений** — `health_core/guards.py:74, 89, 122`
   `_lean_loss_ratio` считает `abs(d_lean)/abs(d_weight)` без проверки знаков. В результате «критический» алерт «потеря мышц» срабатывает и на **здоровом наборе мышечной массы**, и на рекомпозиции тела (жир уходит, мышцы растут) — то есть на объективно лучшем исходе. Пороговый эффект «мальчик кричал волк»: когда случится настоящая потеря мышц, пользователь скорее проигнорирует и её.
   **Фикс:** условие должно быть `if d_lean < 0: ...` (сам факт потери тощей массы), независимо от знака `d_weight` — иначе пропустите опасный случай «набор веса за счёт жира при потере мышц».

3. **FFMI_FLOOR слеп к полу** — `health_core/guards.py:133-152`, порог `config.yaml:86` (19.0 кг/м² один на всех)
   Комментарий в коде сам называет порог «для взрослого мужчины», но `sex` не читается вовсе, хотя соседний гард `check_whr` уже разводит мужской/женский пороги. Для женщин (типичный FFMI 14-17) это перманентный ложный «critical»-алерт о саркопении, обесценивающий сигнал.
   **Фикс:** завести `ffmi_floor_m`/`ffmi_floor_f`, выбирать по `users.sex`, как в `check_whr`.

4. **`ESSENTIAL_FAT_PCT` в forecast.py тоже не зависит от пола** — `health_core/forecast.py:108-110, 231`
   Docstring сам говорит «неснижаемый жир у мужчин ~5%», но применяется и к женщинам (у которых физиологическая норма ~10-13%). Симуляция «безопасно» доводит прогноз похудения женщин до биологически недостижимого/опасного уровня жировой массы, прежде чем остановиться.
   **Фикс:** развести `ESSENTIAL_FAT_PCT_M/_F` по полу.

5. **Macro-минимум физически не влезает в свою же цель по калориям** — `health_core/energy.py:106-148, 382-392`
   `kcal_floor` считает пол калорий по `fat_pct_min=0.20`, а реальные граммы жира в `daily_target` считаются по номинальному `fat_pct=0.30` — на нижнем пороге белок+жир суммарно превышают `kcal_target` (проверено численно: FFM=70кг → 693 ккал белка+жира внутри цели в 630 ккал, при этом углеводы уже заклэмплены в 0). План физически невыполним в трекере на самом низком безопасном калораже.
   **Фикс:** пересчитывать `fat_g` по факту не выше `fat_pct_min`, когда включён `floor_reason == "macro_minimum"`.

6. **`adaptive_tdee` не параметризован датой** — `health_core/energy.py:173, 297`
   Всегда считает окно от реального «сегодня» сервера, даже когда `daily_target` вызывается ретроактивно за прошлую дату. Ломает идемпотентность пересчётов и историю адаптации метаболизма в БД.
   **Фикс:** добавить параметр `date` и пробрасывать его из `daily_target`.

### 🟠 Средней критичности (логика/гардрейлы)

7. **UNDEREATING засчитывает незавершённый «сегодня»** — `health_core/guards.py:157-178` — цикл включает `i=0`, из-за чего алерт «3 дня недоедания подряд» может сработать в середине текущего дня, до того как пользователь доел.
8. **LIPID_GUARD молчит именно в самом опасном случае** — `health_core/guards.py:293-294` — приём препарата совсем без еды рядом (`n==0`) не проверяется, хотя это и есть целевой опасный сценарий (жирорастворимый препарат натощак). Рекомендация: не убирать принцип «нет данных → не судим», а завести отдельный мягкий сигнал `LIPID_GUARD_NO_FOOD`.

### 🔴 Безопасность и надёжность (найдено Analyst-Quality)

9. **Stored XSS / инъекция в веб-панели** — `admin/pages.py:1341, 1482, 1690` (примерно) — переменные из БД (`date`, `sport_val`, `name`) подставляются в HTML/атрибут `onsubmit="confirm('...')"` без экранирования через уже существующую `_e()`. CSP разрешает `unsafe-inline` (`admin/server.py:391`), т.е. пейлоад реально выполнится в сессии администратора.
10. **Zip Slip / path traversal** — `admin/server.py:180-181` — `zf.extractall(extract_dir)` без проверки путей внутри архива. Вредоносный zip с `../../../etc/cron.d/...` может писать файлы вне целевой директории → потенциальный RCE.
11. **Блокировка БД при параллельных tool calls** — `bot/llm.py:355` — `asyncio.gather` запускает несколько write-инструментов параллельно; SQLite допускает одну активную запись, из-за чего `log_food` + `log_water` в одном ответе модели может дать `database is locked` и оборвать цикл. **Фикс:** последовательный запуск записывающих tool calls либо глобальный `asyncio.Lock()`.
12. **Потеря калорий TCX из-за незакрытого флага состояния** — `health_core/ingest/tcx.py:38-42` — `in_lap` выставляется в `True` на `Lap`, но никогда не сбрасывается на `end`, поэтому проверка `not in_lap` для `<Calories>` никогда не проходит — калории тренировок из TCX **молча теряются всегда**.
13. **Неограниченная выборка истории чата** — `bot/history.py:61-62` — весь диалог пользователя от начала времён вычитывается в память перед обрезкой; на 1GB RAM это верный путь к OOM по мере роста истории. **Фикс:** `LIMIT` на уровне SQL, не в Python.
14. **`conn.commit()` внутри доменного ядра** — `health_core/energy.py:405` — нарушает границы транзакций вызывающего кода, при ошибке на следующем шаге `rollback()` уже не спасёт.
15. Необработанные `ValueError` в `health_core/ingest/anthro.py:16-24` и `tcx.py:68-69` роняют весь процесс импорта на одной некорректной строке/дате.

### 🟡 Расхождения документации и кода (найдено Analyst-Consistency)

16. **SPEC.md описывает несуществующий рантайм** — весь документ говорит про Hermes Agent (`~/.hermes/plugins/...`), а реально работает собственный `bot/` на aiogram; отражено только в одной строке комментария `config.yaml:157`.
17. **Контракт инструментов в SPEC вдвое меньше реального** — SPEC насчитывает 13 инструментов, реально зарегистрировано 30 (`plugin/schemas.py`).
18. **`Core/instructions_for_ai.md` и `Core/logic_and_workflow.md` прямо противоречат актуальным гардрейлам** — предписывают абсолютные пороги (75.0 кг, BMR 2092 ккал), которые SPEC.md §10 отдельно объясняет как убранные и замененные на относительные. Если эти файлы когда-либо попадут в промпт — модель получит взаимоисключающие инструкции.
19. **Кэш конфига не инвалидируется между процессами** — `health_core/config.py` держит `@lru_cache`, админка (`admin/server.py`) — отдельный OS-процесс; правка порога через веб-UI подтверждается как успешная, но бот продолжает жить со старым значением до перезапуска. Тихий, практически необнаружимый баг.
20. **`health_core/models.py` не синхронизирован с миграциями `db.py`** — датаклассы `FoodLog`, `DailyTarget` не содержат полей, которые база данных уже имеет (`meal_slot`, `fat_g_target` и др.) — код, который попробует собрать их через `row_to()`, упадёт с `TypeError`.

**Полные детальные разборы с примерами и цитатами — в `analyst_logic_final.md`, `analyst_quality.md`, `analyst_consistency.md`.**

## 5. Побочный результат: установлен инструмент `llm-council`

По ходу сессии вы попросили установить `github.com/am-will/llm-council` — многоагентный планировщик (несколько «планировщиков» пишут независимые планы, затем судья их объединяет). Установлено:
- Репозиторий: `~/llm-council`
- Зарегистрирован как user-level Claude Code скилл через симлинк `~/.claude/skills/llm-council` → должен появиться в списке `/skill` после перезапуска сессии.
- Конфиг `~/.config/llm-council/agents.json` настроен на реально доступные в этом окружении CLI: **`agy` (Gemini) вместо `claude`**, потому что `kind: "claude"` в родном скрипте жёстко требует `--dangerously-skip-permissions`, а среда, в которой мы работаем, запрещает создание таких «небезопасных» вложенных агентов под root (я специально это не обходил — сработал ваш собственный guardrail на «Create Unsafe Agents»).
- **Не протестировано end-to-end живьём** — Gemini-квота (тот же лимит, что помешал первому проходу анализа) ещё не сброшена (~2 часа с момента исчерпания). Как только квота восстановится, стоит прогнать тестовую задачу через `python3 ~/llm-council/scripts/llm_council.py run --spec <файл> --no-ui`, чтобы убедиться, что всё работает как задумано.

## Итог

Система спроектирована с хорошей медицинской методологией (относительные пороги, отказ вместо выдумывания цифр), но содержит один по-настоящему опасный вычислительный баг (инвертированный знак TDEE, пункт 1) и несколько ложных критических алертов из-за отсутствия проверки направления/пола в гардах. Отдельно — реальные security-дыры в веб-панели (XSS, Zip Slip), которые стоит закрыть до следующего раза, когда админка будет открыта наружу. Документация (SPEC.md, Core/*.md) требует либо обновления, либо явной пометки «архив» — расхождение с кодом уже достаточно большое, чтобы вводить в заблуждение любого, кто будет разбираться в системе (включая будущего вас через полгода).
