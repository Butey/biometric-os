**Сводка: Топ-7 проблем качества кода и безопасности (по убыванию критичности)**

В ходе глубокого статического анализа кодовой базы Telegram-агента обнаружены серьезные уязвимости безопасности и архитектурные дефекты, напрямую влияющие на стабильность (особенно в условиях 1GB RAM) и целостность данных.

1. **[Критично / Безопасность] Stored XSS и инъекция кода** в веб-панели через неэкранированные значения базы данных.
2. **[Критично / Безопасность] Уязвимость Zip Slip** при распаковке файлов тренировок, открывающая вектор для атаки Path Traversal / RCE.
3. **[Высокий / Надежность] Отказ в обслуживании БД (Database is locked)** из-за параллельного запуска инструментов записи.
4. **[Высокий / Целостность] Потеря данных о калориях TCX** из-за ошибки конечного автомата (невозврат флага состояния) при парсинге XML.
5. **[Средний / Производительность] Утечка памяти/OOM из-за неограниченной SQL-выборки** при каждом сообщении (чтение всей истории диалога).
6. **[Средний / Надежность] Необработанные исключения (`ValueError`)** при конвертации дат и чисел, вызывающие падение всего процесса импорта.
7. **[Средний / Архитектура] Неконтролируемые фиксации транзакций (`commit`)** внутри доменных функций ядра, ломающие атомарность вызывающего слоя.

---

### Детальные находки

#### 1. Stored XSS и инъекция JS-кода в HTML-атрибуты
- **Файл:Строка:** `admin/pages.py:1682-1689`, `1340-1347`, `1482`.
- **Проблема:** Переменные из БД (`sport_val`, `date`, `name`) конкатенируются напрямую в HTML-разметку (например, `<h3>{date}</h3>` или атрибут `onsubmit="return confirm('Удалить {name}?');"`) без предварительного экранирования.
- **Влияние:** Злоумышленник, пользователь или галлюцинирующая LLM могут внедрить вредоносный JavaScript-пейлоад в название тренировки или дату плана. Учитывая, что CSP (`server.py:391`) разрешает `unsafe-inline`, скрипт будет выполнен в браузере с сессией администратора. Дополнительно, кавычки в `confirm` сломают синтаксис скрипта.
- **Исправление:** Обязательно оборачивать все динамические строковые переменные в функцию экранирования `_e()` перед подстановкой в f-строки. Для атрибутов `onsubmit` следует отказаться от инлайн-JS в пользу использования `data-`-атрибутов и глобального слушателя событий.

#### 2. Уязвимость Zip Slip при обработке загрузок
- **Файл:Строка:** `admin/server.py:180-181`.
- **Проблема:** Функция `zf.extractall(extract_dir)` распаковывает ZIP-архив без проверки путей вложенных файлов.
- **Влияние:** Если загружаемый файл содержит элементы с путями вида `../../../etc/cron.d/malicious`, `extractall` покорно извлечет их вне целевой директории `extract_dir`, перезаписывая системные файлы сервера, что ведет к Remote Code Execution (RCE).
- **Исправление:** Заменить вызов `extractall()` на безопасную ручную распаковку через перебор `zf.infolist()`. Игнорировать или исправлять пути, если `os.path.isabs(info.filename)` равно `True` или если путь содержит компонент `..`.

#### 3. Блокировка базы данных при параллельном вызове инструментов
- **Файл:Строка:** `bot/llm.py:355` (`results = await asyncio.gather(...)`).
- **Проблема:** Вызовы инструментов от LLM (`_run_one`) запускаются строго параллельно через `asyncio.to_thread`. Многие инструменты (`log_food`, `log_water`) выполняют операции `INSERT/UPDATE` в базу данных.
- **Влияние:** SQLite даже в режиме WAL разрешает ровно одну активную транзакцию на запись. Если модель решит залогировать воду и еду в одном ответе, два параллельных потока столкнутся, вызывая критическую ошибку `sqlite3.OperationalError: database is locked`, которая прервет агентный цикл.
- **Исправление:** Переписать запуск инструментов на строго последовательный: итеративный цикл `for call in tool_calls: result = await _run_one(...)`, либо внедрить глобальный асинхронный мьютекс (`asyncio.Lock()`), оборачивающий запись в БД.

#### 4. Потеря метрик калорий из-за ошибки автомата в XML парсере
- **Файл:Строка:** `health_core/ingest/tcx.py:38-42`.
- **Проблема:** При стриминговом чтении `ET.iterparse` флаг состояния `in_lap` становится `True` при открытии узла `Lap` (строка 38). Однако в коде **отсутствует сброс** этого флага на событии `end` для узла `Lap`.
- **Влияние:** Блок `<Calories>` в файлах TCX часто следует после тега `Lap` или внутри него. Так как `in_lap` навсегда остается `True`, проверка `elif tag == "Calories" and not in_lap:` не сработает никогда. Система молча игнорирует калории во всех импортированных TCX-тренировках.
- **Исправление:** Добавить обработчик закрытия: `if event == "end" and tag == "Lap": in_lap = False`.

#### 5. Неограниченная SQL-выборка истории (OOM / Утечка производительности)
- **Файл:Строка:** `bot/history.py:61-62`.
- **Проблема:** Запрос `SELECT ts, role, content FROM chat_history WHERE telegram_user_id=? ORDER BY rowid ASC` выгружает весь диалог пользователя целиком от начала времен, и только потом `_trim` обрезает массив в оперативной памяти.
- **Влияние:** При длительном использовании системы таблица разрастается. На каждое новое сообщение агент десериализует тысячи JSON-объектов. При лимите 1 ГБ RAM на сервере процесс бота неизбежно упрется в OOM (Out of Memory) и будет убит системой, а задержка перед ответом (Time-to-First-Byte) увеличится до секунд.
- **Исправление:** Ограничить выборку на уровне СУБД с помощью подзапроса: `SELECT * FROM (SELECT ts, role, content FROM chat_history WHERE telegram_user_id=? ORDER BY rowid DESC LIMIT 50) ORDER BY rowid ASC`.

#### 6. Жесткие падения процессов импорта на `ValueError`
- **Файл:Строка:** `health_core/ingest/anthro.py:16-24` и `health_core/ingest/tcx.py:68-69`.
- **Проблема:** В `_parse_value` отсутствует перехват ошибок при вызове `float(s)`. Аналогично, `strptime(..., "%Y-%m-%dT%H:%M:%S.%fZ")` падает, если в TCX время записано в ISO без долей миллисекунд (например, `10:00:00Z`).
- **Влияние:** Обычная текстовая опечатка в дневнике антропометрии или валидный (но неполный) формат ISO-времени приводят к необработанному исключению, полному прерыванию процесса импорта и, возможно, возврату технической ошибки пользователю бота.
- **Исправление:** Обернуть вызовы `float()` и `strptime` в конструкцию `try...except ValueError:`, чтобы при ошибке функция возвращала `None` и некорректная точка элегантно отбрасывалась без остановки пайплайна.

#### 7. Нарушение атомарности из-за `commit()` в доменном ядре
- **Файл:Строка:** `health_core/energy.py:405`.
- **Проблема:** В конце расчетной функции `daily_target()` жестко прописан вызов `conn.commit()`.
- **Влияние:** Нарушение принципа управления транзакциями (Transaction Boundary). Если функция вызывается в цикле или как часть комбинированного инструмента, `conn.commit()` зафиксирует в БД все внешние, еще не проверенные изменения. В случае падения на следующем шаге `rollback()` уже не сработает, и в базе останется "грязное" состояние (partial writes).
- **Исправление:** Полностью удалить `conn.commit()` из функций в пакете `health_core`. Управление транзакциями (commit/rollback) должно выполняться исключительно на уровне точек входа: в хендлерах `plugin/tools.py` или скриптах-оповещениях `scripts/`.
