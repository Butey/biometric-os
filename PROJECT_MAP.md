# Карта проекта Health Agent System (Метаболический контур)

Данный документ содержит архитектурную карту кодовой базы, описание зон ответственности каталогов и файлов, а также **рекомендации и готовые предложения для Claude**, позволяющие кардинально сократить расход токенов при работе с проектом и самостоятельно составить рабочие инструкции.

---

## 1. Паспорт проекта и ключевые инварианты

- **Назначение:** Персональный Telegram-ассистент для снижения жировой массы с сохранением скелетной мускулатуры у людей на терапии препаратами GLP-1 (тирзепатид, семаглутид и др.).
- **Стек технологий:**
  - Язык и среда: Python 3.13, виртуальное окружение `.venv/bin/python`
  - Telegram-транспорт: `aiogram 3`
  - База данных: SQLite (`health.db`), чистый SQL без тяжелых ORM
  - Панель администратора: stdlib `http.server` application with HTML built in `admin/pages.py`
  - Фоновые службы: `systemd` (сервисы и таймеры для пользователя)
  - LLM-интеграция: асинхронный клиент на `aiohttp`, цепочка OpenAI-совместимых провайдеров (Gemini, Groq, Nvidia, DeepSeek) с fallback-логикой и Prompt Caching.

### Фундаментальные архитектурные инварианты:
1. **Детерминированная арифметика:** Языковая модель **никогда не производит математических расчетов** (калории, дефициты, граммы БЖУ, ступени титрации доз, динамика веса, даты вех). Все вычисления производятся исключительно детерминированным кодом на Python в `health_core/`. Модель отвечает только за ведение диалога на естественном языке, распознавание сущностей и вызов соответствующих инструментов.
2. **SQLite — единственный источник истины:** Никакая фактура не извлекается из истории переписки. Все данные (замеры, приемы пищи, лекарства, симптомы, настройки) считываются из SQLite и сохраняются в нее.
3. **Строгая изоляция слоев:** Модули `health_core/` не содержат зависимостей от `bot/`, `aiogram`, Telegram или сети. Вся доменная логика тестируема автономно без внешних сервисов.
4. **Контракт инструментов:** `plugin/tools.py` регистрирует инструменты через интерфейс `register(ctx)`. Модуль `bot/registry.py` предоставляет shim `_RegistryCtx`, адаптируя их в OpenAI-совместимый формат схем, и пробрасывает идентификатор пользователя (`telegram_id`) через `ContextVar`.

## 2. Архитектурная карта каталогов и модулей

```
health_agent_system/
├── health_core/         # Детерминированная доменная логика (без внешних зависимостей)
├── bot/                 # Собственный цикл агента (aiogram 3, вызовы LLM, история диалога)
├── plugin/              # Спецификации и хендлеры 35 инструментов (tools.py, schemas.py)
├── scripts/             # Cron-скрипты автоматических расписаний (--no-agent) и notify.py
├── admin/               # Веб-панель управления (stdlib http.server)
├── Core/                # Системный промпт Telegram-бота (персона, тон, правила)
├── Knowledge/           # Статьи доказательной базы знаний для RAG-инструмента knowledge
├── Metrics/             # Хранилище входящих данных (выгрузки весов, TCX, CSV)
├── Nutrition/           # Материалы и дневники питания
├── config.yaml          # Конфигурация метаболических формул, порогов и провайдеров LLM
├── test_bot.py          # 25 сценариев цикла агента офлайн (без сети и Telegram)
├── test_e2e.py          # 10 сквозных стадий проверки доменной логики на реальных данных
└── migrate.py           # Идемпотентный импорт истории пользователя
```

### 2.1. Доменное ядро (`health_core/`)
- `db.py`: подключение к SQLite, транзакции, создание схемы, таблицы пользователей, замеров, приемов пищи, фармакотерапии, анализов, логов консилиума.
- `models.py`: типизированные структуры данных предметной области.
- `config.py`: синтаксический разбор `config.yaml`, работа с локальным временем пользователя (`local_now()`).
- `energy.py`: метаболическая модель:
  - Формулы BMR (Mifflin-St Jeor / Katch-McArdle) и TDEE.
  - Лимит отдачи жира Alpert (69.3 ккал/кг жировой массы в сутки).
  - Динамическая допустимая доля дефицита (`fat_share`) в зависимости от процента жира.
  - Пол калорий (`kcal_floor`) — нижняя граница безопасности, защищающая мышечную ткань.
  - Макро-минимум и распределение БЖУ (белок: 1.8 г/кг тощей массы, жиры: 20-35% энергии).
- `guards.py`: 12+ клинических защитных барьеров (гардрейлов):
  - Контроль максимального темпа снижения веса (профилактика желчнокаменной болезни).
  - Проверка адекватности потребления белка.
  - Защита от дефицита глубже пола калорий.
  - Контроль соблюдения ступеней титрации GLP-1 и пауз в терапии (>14 дней).
- `glp1.py`: фармакокинетическая модель концентрации GLP-1 препаратов (период полувыведения, накопление, стационарный уровень).
- `meds.py`: регистрация инъекций и лекарств, контроль лестниц титрации, расчет остатка препарата в днях терапии.
- `card_drafts.py`: черновики фармакологических карт препаратов (генерация из данных openFDA и ClinicalTrials.gov, валидация полей на границе доверия).
- `chrono.py`: распознавание окон питания (завтрак, обед, ужин, перекус) и учет часовых поясов.
- `labs.py`: биомаркеры лабораторных анализов крови и расчет производных индексов (HOMA-IR, eGFR, TyG, TG/HDL, AIP, FIB-4).
- `hr_zones.py`: расчет максимального пульса (HRmax) и 5 пульсовых тренировочных зон.
- `report.py`: генерация статус-бара (`get_status_bar`), дневной сводки (`get_day_summary`), трендов (`get_trends`), недельного отчета.
- `forecast.py`: вероятностная экстраполяция динамики массы тела и прогнозирование достижения вех с интервалами неопределенности.
- `refeed.py`: поддержка протокола перемежающейся диеты MATADOR (фазы дефицита и эукалорийного поддержания).
- `sick.py`: режим болезни (деактивация дефицита калорий, отключение жестких уведомлений).
- `council_data.py`: подготовка обезличенного, детерминированного пакета данных за многодневный период для консилиума моделей.
- `export.py`: полный экспорт профиля пользователя (JSON/CSV) и резервное копирование SQLite БД.
- `ingest/`: парсеры внешних источников данных:
  - `scale.py`: парсинг выгрузок умных весов (Excel, CSV).
  - `tcx.py`: парсинг спортивных тренировок Garmin TCX.
  - `anthro.py`: замеры окружностей тела (сантиметровая лента).
  - `diary.py` и `sleep.py`: парсинг сторонних дневников и логов сна.

### 2.2. Цикл агента (`bot/`)
- `main.py`: входная точка Telegram-бота на `aiogram 3`. Обработка сообщений, белый список (`TELEGRAM_ALLOWED_USERS`), быстрые макросы, слэш-команды без вызова LLM, изоляция блокировок пользователей (`user_lock`).
- `llm.py`: сетевой слой взаимодействия с языковыми моделями на `aiohttp`. Пул провайдеров, фолбэк при исчерпании лимитов или сбоях, цикл выполнения tool calls (`max_tool_iters: 12`), поддержка заголовков Prompt Caching.
- `registry.py`: реестр 35 инструментов, преобразование схем в формат OpenAI Function Calling, синхронный диспетчер `dispatch(name, args)`, установка личности пользователя в `ContextVar`.
- `history.py`: управление контекстом диалога в SQLite со скользящим окном (лимит по числу сообщений и лимит по объему символов).
- `knowledge.py`: RAG-модуль поиска релевантных статей по базе знаний в `Knowledge/`.
- `council.py`: оркестратор фонового консилиума независимых моделей (аналитики + итоговый судья) при выходе на плато или пересмотре дозировок.

### 2.3. Инструменты (`plugin/`)
- `tools.py`: 35 обработчиков действий (логирование еды, воды, веса, фармакотерапии, анализов, запуск консилиума и т.д.).
- `schemas.py`: строгие JSON-схемы входных параметров для каждого инструмента.
- `plugin.yaml`: манифест плагина со списком предоставляемых инструментов.

### 2.4. Фоновые сценарии (`scripts/`)
Скрипты запускаются по расписанию в режиме `--no-agent` (печать отчетов в stdout). Модуль `notify.py` оборачивает их вызов и отправляет форматированные сообщения в Telegram:
- `dispatch.py`: диспетчер рассылки задач с привязкой к локальному времени каждого пользователя.
- `morning_checkin.py`: утренний запрос веса и самочувствия.
- `meal_window_check.py`: проверка внесения приемов пищи по завершении окон питания.
- `evening_report.py`: подведение итогов дня и проверка соблюдения целей.
- `weekly_recalc.py`: еженедельный пересчет метаболических параметров и трендов.
- `injection_reminder.py`: напоминание об очередном дне инъекции GLP-1.
- `export_backup.py`: создание ночного бэкапа базы данных.

### 2.5. Веб-панель администратора (`admin/`)
- `server.py`: веб-приложение на stdlib `http.server`.
- `pages.py`: HTML-страницы (управление пользователями, графики метрик, верификация черновиков карт лекарств `/drafts`, управление базой знаний `/knowledge`).
- `auth.py`: сессионная авторизация администратора по паролю.
- `upload.py`: загрузка файлов весов, тренировок и анализов через веб-интерфейс.

## 4. Предложения и рекомендации для Claude (Token Reduction & Best Practices)

Чтобы Claude при решении задач не расходовал лишние токены и не перегружал контекст, рекомендуется следовать следующим правилам.

### 4.1. Правила навигации и точечного чтения (Экономия токенов)
1. **Запрет на полное чтение сверхбольших файлов:**
   - `plugin/tools.py` (~352 КБ, >90k токенов) — содержит реализацию всех инструментов. Никогда не читайте его целиком! Используйте `grep` по имени инструмента (например, `def _handle_log_food`) и просматривайте только конкретную функцию (30-60 строк).
   - `health_core/guards.py` (~115 КБ, >30k токенов) — ищите конкретный гардрейл по названию (`grep "def check_"`) и читайте точечный срез строк.
   - `admin/pages.py` (~141 КБ) и `admin/server.py` (~90 КБ) — читайте только интересующий маршрут или страницу.
   - `SPEC.md` (~57 КБ) и `architecture.html` (~82 КБ) — не читайте для решения рядовых задач; вся актуальная выжимка структуры уже приведена в этом документе.
2. **Исключение «шумных» каталогов и логов:**
   - Папки `_agent_swarm_analysis/`, `research/`, `llm-council/runs/`, `Nutrition/`, `Metrics/`, `Обучение/`, `gemini_edited/` содержат массивные исторические дампы и бинарные файлы. Их сканирование или поиск по ним через ripgrep без сужения области сжигает от 50k до 200k токенов за вызов. Не ищите в них код.
3. **Прямая маршрутизация по карте:**
   - Если нужно изменить расчет калорий или дефицита $\rightarrow$ сразу открывайте `health_core/energy.py`.
   - Если нужно изменить логику проверки титрации $\rightarrow$ сразу открывайте `health_core/guards.py` или `health_core/glp1.py`.
   - Если нужно поправить сетевой вызов к LLM или prompt caching $\rightarrow$ `bot/llm.py`.
   - Если нужно скорректировать логику телеграм-хендлеров $\rightarrow$ `bot/main.py`.

### 4.2. Инварианты при генерации и правке кода
- **Никаких вычислений на стороне промпта:** Если добавляется новая метрика или формула, она реализуется в `health_core/`, а боту отдается через готовый инструмент или поле сводки.
- **Сохранение сигнатур и изоляции:** Не импортировать ничего из `bot/` в `health_core/`.
- **Контекст пользователя:** При вызове инструментов в синхронном коде всегда помнить о пробросе идентификатора через `_CALLER_FALLBACK` (`registry.set_caller(telegram_id)`).

### 4.3. Окружение и команды верификации
- **Интерпретатор:** Всегда используйте виртуальное окружение проекта: `.venv/bin/python` (Python 3.13).
- **Сквозная проверка бота (без сети):**
  ```bash
  .venv/bin/python test_bot.py
  ```
  *(Прогоняет 25 сценариев цикла агента: проверку схем, диспетчеризацию, allowlist, изолированность пользователей, слэш-команды, блокировки).*
- **Интеграционная проверка доменной логики:**
  ```bash
  .venv/bin/python test_e2e.py
  ```
  *(Прогоняет 10 стадий на реальных данных: регистрацию, импорт замеров, питание, воду, гардрейлы, статус-бар, экспорт).*
- **Автономные проверки модулей:**
  ```bash
  .venv/bin/python -m health_core.db
  .venv/bin/python -m health_core.energy
  .venv/bin/python -m health_core.guards
  .venv/bin/python -m bot.registry
  .venv/bin/python -m bot.llm
  ```

### Как запускать проверки
- `.venv/bin/python test_bot.py` (52 теста, работает на временной БД, не трогает живую БД)
- `.venv/bin/python -m bot.history` - история и compact
- `.venv/bin/python -m health_core.guards` - гарды.

### Гарды глюкозы и пульса (кратко)
- `GLUCOSE_VOLATILITY` (код оставлен, смысл сменился): 3 последних замера натощак подряд выше своей медианы за 28 дней на 0.3 ммоль/л и больше; замеры не натощак и после сна <6 ч не считаются; severity `info`; в тексте уверенность, точки сигнала, «наблюдать динамику».
- `RESTING_HR_RISING`: медиана `hr_min` за 7 дней минус медиана за предыдущие 28 дней >= 4 уд/мин; severity `info`; глушится режимом болезни.

### Правила, которые легко сломать
- Чек-лист и гарды: галочка `✓` - записано, `☐` - нет.
- `find_mine(loose=True)` по умолчанию; `forget` обязан звать с `loose=False`, иначе удалит не тот продукт.
- Тесты, которые пишут в БД, должны ставить `HEALTH_DB` ДО импорта модулей, тянущих `health_core.db` (иначе пишут в живую `/root/.hermes/health.db`). У `meal_options.py` это учтено отложенным импортом `report`.
- Файлы с CRLF (`guards.py`, `report.py`, `export.py`, `schemas.py`, `registry.py`, `system_promt.md`): править с сохранением окончаний строк, иначе дифф на тысячи строк.
