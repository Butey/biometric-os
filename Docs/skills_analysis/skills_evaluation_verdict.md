## Контекст проекта (выводы ридера)

Проанализировано **34 файла** документации. Ключевые факты:

- **Профиль:** Персональный Telegram-агент для одного пользователя (Python-разработчик, 183 см, старт 158.8 кг → цель 100–110 кг, LBM > 80 кг)
- **Железо:** 1 vCPU / 1 GB RAM + 2 GB swap. Никаких GPU. Никаких тяжелых ML-моделей
- **Философия:** Вся арифметика — детерминированный Python. LLM только парсит текст и вызывает инструменты. Числа модель не придумывает
- **Медконтекст:** Тирзепатид 12.5 мг (GLP-1/GIP), Тесторил (андрогенная поддержка), разрыв ПКС (запрет ударных нагрузок), ожирение II–III ст.
- **Уже реализовано:** 24 инструмента, 27 файлов базы знаний, адаптивный TDEE по Холлу, MATADOR-рефиды, 6 гардрейлов (LBM_RATIO, LBM_DRIFT, FFMI_FLOOR, PLATEAU, UNDEREATING, BMR Floor)
- **Хорошо покрыто:** Питание (подробнейше), поведенческая психология голода (3 типа, РПП, осознанное питание), сон (CBT-I), тренировки при ожирении с травмой, фармстек

## Вердикты по каждому блоку

### Блок 6: Предиктор срывов (Binge Risk Triad)

| | |
|---|---|
| **Вердикт** | ✅ **ВНЕДРЯТЬ (приоритет №1)** |
| **Релевантность** | 10/10 |
| **Сложность** | 2/10 |
| **ROI** | 10/10 |

**Позиция аналитика:** Внедрять. «Binge Risk Triad» — блестящая концепция. Реализуется простым Python-скриптом.

**Мой вердикт: Полностью согласен. Это жемчужина всего исследования.**

Триада риска срыва (накопленный дефицит > 3500 ккал за 5 дней + сон < 6.5 ч + белок на завтрак < 20 г) — это именно тот тип аналитики, для которого проект и создан. Все данные уже есть в SQLite (`food_log`, `sleep_log`, таймстемпы приемов пищи). Вычисление — чистый Python, без внешних зависимостей.

**Что дает:** Проактивный пуш в Telegram *до* срыва, а не анализ *после*. Идеально дополняет базу знаний «Еда без хаоса» (2094 строки) и три файла о типах голода.

**Реализация:** Cron-скрипт в `scripts/` → проверка триады → `notify.py` → Telegram.

### Блок 5: Фармакокинетика GLP-1 (Тирзепатид)

| | |
|---|---|
| **Вердикт** | ✅ **ВНЕДРЯТЬ (приоритет №2)** |
| **Релевантность** | 10/10 |
| **Сложность** | 3/10 |
| **ROI** | 10/10 |

**Позиция аналитика:** Внедрять. Моделирование t½ критически важно для пользователя на тирзепатиде.

**Мой вердикт: Согласен. Прямое попадание в медконтекст проекта.**

Пользователь *уже* принимает тирзепатид 12.5 мг, и система *уже* трекает инъекции через `pharma` и `log_med`. Добавление экспоненциального распада ($C(t) = C_0 \times e^{-kt}$, $t_{1/2} \approx 5$ дней для тирзепатида) позволит:
- Предсказывать дни максимального подавления аппетита (пик концентрации)
- Планировать рефиды на дни минимальной концентрации (перед следующей инъекцией)
- Корректировать калорийность на основе ожидаемого эффекта препарата

**Нутрицевтическая матрица (синергия БАД):** Тоже внедрять, но как справочную таблицу в Knowledge/, а не как программный модуль. Правила простые (железо не с кальцием, D3 с жирами, магний перед сном) — достаточно текстового гайда для LLM.

### Блок 4: Хрононутрициология (TRE, Late Caloric Load, Caffeine Cutoff)

| | |
|---|---|
| **Вердикт** | ✅ **ВНЕДРЯТЬ (приоритет №3)** |
| **Релевантность** | 9/10 |
| **Сложность** | 2/10 |
| **ROI** | 9/10 |

**Позиция аналитика:** Внедрять. Все данные уже есть в `log_food` и `log_sleep`. SQL + Python = мгновенная аналитика.

**Мой вердикт: Согласен. Нулевые затраты ресурсов, максимум инсайтов.**

Конкретно:
- **TRE (пищевое окно):** Разница между первым и последним `log_food` за день. Простейший SQL. Корреляция с качеством сна из `log_sleep`.
- **Late Caloric Load:** Доля калорий за последние 3 часа перед `bedtime` из `log_sleep`. Связь с утренним сахаром из `log_glucose`.
- **Caffeine Cutoff:** Простейшая формула ($\text{остаток} = \text{доза} \times 0.5^{t/5.5}$). Персональный расчет «последний кофе не позже HH:MM» на основе времени засыпания.

**Модель Понтцера** (нелинейная компенсация TDEE при большом кардио): В проекте уже есть дисконт TCX × 0.75. Модель Понтцера — теоретическое уточнение, но на практике дисконт 0.75 уже выполняет ту же функцию грубо. **Не приоритет**, но стоит упомянуть в Knowledge/ как обоснование существующего дисконта.

### Блок 1: Лабораторная диагностика и биомаркеры

| | |
|---|---|
| **Вердикт** | ⚠️ **ЧАСТИЧНО (приоритет №4)** |
| **Релевантность** | 8/10 |
| **Сложность** | 2/10 (формулы) / 9/10 (OCR) |
| **ROI** | 7/10 |

**Позиция аналитика:** Только формулы (HOMA-IR, eGFR, eAG). Ввод текстом. Никакого OCR.

**Мой вердикт: Согласен, но с уточнением.**

> [!IMPORTANT]
> Формулы HOMA-IR и eGFR напрямую релевантны: пользователь на тирзепатиде (контроль инсулинорезистентности) и высокобелковой диете (контроль почек). Это стоит добавить.

**Что взять:**
- `log_labs` — новый инструмент для ручного ввода результатов анализов (текст: «Глюкоза 5.2, инсулин 8.3, креатинин 92»)
- Детерминированные формулы: HOMA-IR, eGFR (CKD-EPI 2021), Non-HDL, eAG
- Привязка к вехам (`milestones.md` уже требует проверку липидограммы и АЛТ/АСТ на весе 140 кг)

**Что НЕ брать:**
- Любой OCR/парсинг PDF (PaddleOCR, Nougat, Unstructured) — гарантированный OOM на 1 GB RAM
- Репозитории ToolUniverse и Open-Medica — избыточны для 5 формул

### Блок 2: Мультимодальный контур (штрих-коды, фото, голос)

| | |
|---|---|
| **Вердикт** | ⚠️ **ЧАСТИЧНО (приоритет №5)** |
| **Релевантность** | 5/10 |
| **Сложность** | 3/10 (штрихкоды) / 8/10 (остальное) |
| **ROI** | 4/10 |

**Позиция аналитика:** Только OpenFoodFacts API по текстовому штрихкоду. Никакого Vision и локального Whisper.

**Мой вердикт: Согласен с аналитиком, но добавлю нюанс по голосу.**

**Что взять:**
- **OpenFoodFacts API** — легковесный HTTP-запрос по номеру штрихкода. Пользователь фотографирует штрихкод в Telegram → бот передает цифры → `fetch_openfoodfacts(barcode)` → точный КБЖУ. Библиотека `openfoodfacts-python` весит ничего, зависимость только `requests`.

**Что НЕ брать:**
- **Локальный Whisper/faster-whisper** — модель `tiny` занимает ~150 MB RAM, `base` ~300 MB. На 1 GB это смертный приговор. Если голосовой ввод критически нужен в будущем — только через внешний API (OpenAI Whisper API, стоит $0.006/мин), но это не приоритет.
- **Vision (фото тарелки)** — аналитик прав: это «математика ради математики». У пользователя уже есть подробнейшие шпаргалки по методу тарелки в Knowledge/ и привычка текстового ввода.

### Блок 3: Спортивная физиология (ACWR, 1RM, HRR)

| | |
|---|---|
| **Вердикт** | ❌ **НЕ ВНЕДРЯТЬ** |
| **Релевантность** | 3/10 |
| **Сложность** | 5/10 |
| **ROI** | 2/10 |

**Позиция аналитика:** Игнорировать. ACWR — для элитных атлетов, неактуально при ожирении и травме.

**Мой вердикт: Согласен.**

Аналитик точно выделил ключевое противоречие: ACWR (модель Бэнистера) предназначена для периодизации нагрузки у спортсменов, работающих на пределе. Пользователь с ИМТ ~40, разрывом ПКС и основной активностью в VR — далек от этого контекста.

Единственное исключение — **1RM как косвенный маркер сохранения LBM**. Но:
- Система уже отслеживает LBM напрямую через биоимпедансные весы
- Гарды LBM_RATIO, LBM_DRIFT и FFMI_FLOOR уже покрывают эту задачу
- Добавление 1RM-трекинга создаст дублирование без дополнительной ценности

## Стратегический вывод

Проект «Метаболический контур» — это **снайперская винтовка**, а не швейцарский нож. Его сила — в узком фокусе, детерминированности и жестких гардах. Попытка превратить его в универсальную медицинскую платформу (геномика, DICOM, Drug Discovery) убьет главное преимущество.

**Граница разумного расширения** проходит по линии: «вычислимая аналитика на основе уже собираемых текстовых логов». Блоки 4, 5 и 6 — это именно такая аналитика: нулевые затраты RAM, нулевые внешние зависимости, максимум actionable инсайтов.

Три скилла из топа (предиктор срывов, фармакокинетика GLP-1, хрононутрициология) вместе дают проекту качественный скачок из режима **реактивного** дневника («записал → посчитал → показал») в режим **проактивного** коуча («предупредил → предложил → защитил»).
