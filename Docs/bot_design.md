# Рабочая архитектура

Telegram → `bot/main.py` (aiogram) → `bot/llm.py` → `bot/registry.py` →
`plugin/tools.py` → детерминированное `health_core/` → SQLite.

Hermes не устанавливается и не импортируется. `plugin/` — собственный набор
обработчиков и схем. `register(ctx)` — локальный контракт с реестром бота.
Личность задаётся `registry.set_caller()` через ContextVar, не аргументами LLM.

Общий модуль `health_core/environment.py` читает `.env` в корне проекта.
Бот, панель, CLI и cron используют его; окружение процесса имеет приоритет.
`health.db` лежит рядом с `.env`; относительный `HEALTH_DB` считается от корня.
История — `chat_history`; перед сжатием и очисткой полный снимок сохранённых
записей пишется атомарно в `history_archive/<telegram_id>/<sha256>.json` рядом
с выбранной БД. Ошибка архивации оставляет исходную историю. Замена сообщений
сводкой выполняется транзакционно; архивы сохраняются отдельно от окна LLM.

Отчёты читают записи с учётом даты и времени запроса. Общая оценка динамики
веса вычисляется в `health_core/plateau.py`; доля потери FFM — в
`health_core/body_composition.py`. Ответ модели не должен подменять эти
вычисления разницей двух произвольных замеров или придумывать причину плато.
`/export` и инструмент `export_data` создают архив записей пользователя и
передают его Telegram-транспорту для отправки в собственный личный чат.
