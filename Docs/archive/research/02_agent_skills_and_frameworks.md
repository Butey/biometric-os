### 2.2. Валидированные клинические и метаболические формулы

Ниже приведен детальный разбор ключевых формул, их валидированные диапазоны, единицы измерения и математическая формулировка:

#### 1. HOMA-IR (Homeostatic Model Assessment of Insulin Resistance)
* **Назначение:** Золотой стандарт суррогатной оценки инсулинорезистентности и бета-клеточной дисфункции поджелудочной железы по базальным уровням глюкозы и инсулина натощак.
* **Математическая модель:**
  * В единицах СИ (ммоль/л):
    $$\text{HOMA-IR} = \frac{\text{Глюкоза натощак (ммоль/л)} \times \text{Инсулин натощак (мкЕд/мл)}}{22.5}$$
  * В традиционных единицах (мг/дл):
    $$\text{HOMA-IR} = \frac{\text{Глюкоза натощак (мг/дл)} \times \text{Инсулин натощак (мкЕд/мл)}}{405}$$
* **Пороговые значения:**
  * $< 2.0$ — оптимальная чувствительность к инсулину.
  * $2.0 - 2.7$ — ранняя метаболическая компенсация (серая зона).
  * $> 2.7$ — манифестная инсулинорезистентность.
* **Применение в системе:** Оценка эффективности снижения веса и действия агонистов GLP-1/GIP (тирзепатид) на углеводный обмен.

#### 2. TyG Index (Triglyceride-Glucose Index)
* **Назначение:** Высокоточный маркер метаболического синдрома, стеатоза печени (НАЖБП / MASH) и тканевой резистентности к инсулину. Применяется, когда в панели анализов нет инсулина.
* **Математическая модель:**
  $$\text{TyG} = \ln\left( \frac{\text{Триглицериды (мг/дл)} \times \text{Глюкоза (мг/дл)}}{2} \right)$$
  *Формула прямого пересчета из ммоль/л:*
  $$\text{TyG} = \ln\left( \frac{(\text{TG}_{\text{ммоль/л}} \times 88.57) \times (\text{Glu}_{\text{ммоль/л}} \times 18.0182)}{2} \right)$$
* **Клинические пороги:**
  * $< 8.5$ — метаболическая норма.
  * $8.5 - 8.8$ — риск метаболического синдрома и раннего атеросклероза.
  * $\ge 8.8$ — выраженный риск жирового гепатоза и сосудистых осложнений.

#### 3. eGFR (Estimated Glomerular Filtration Rate) — стандарт CKD-EPI 2021
* **Назначение:** Расчет скорости клубочковой фильтрации по креатинину сыворотки без расового коэффициента (официальный консенсус NKF-ASN / KDIGO 2021). Критически необходим для контроля почек при высокобелковом рационе ($1.6 - 2.4\text{ г/кг FFM}$) и приеме нефроактивных препаратов.
* **Математическая модель:**
  $$\text{eGFR} = 142 \times \min\left(\frac{S_{cr}}{\kappa}, 1\right)^\alpha \times \max\left(\frac{S_{cr}}{\kappa}, 1\right)^{-1.200} \times 0.9938^{\text{Age}} \times [1.012 \text{ if Female}]$$
  Где $S_{cr}$ — креатинин сыворотки в мг/дл ($S_{cr}\text{ [мг/дл]} = S_{cr}\text{ [мкмоль/л]} / 88.4$):
  * Женщины: $\kappa = 0.7$, $\alpha = -0.241$
  * Мужчины: $\kappa = 0.9$, $\alpha = -0.302$
* **Градации ХБП (мл/мин/1.73 м²):**
  * $\ge 90$ — G1 (норма / гиперфильтрация).
  * $60 - 89$ — G2 (незначительное снижение, безопасны стандартные дозы белка).
  * $45 - 59$ — G3a (умеренное снижение, ограничение белка до $\le 1.2\text{ г/кг}$).
  * $< 30$ — G4-G5 (тяжелое поражение, дефициты калорий противопоказаны).

#### 4. Клиренс креатинина по Cockcroft-Gault с коррекцией на ожирение (ABW / IBW)
* **Назначение:** Расчет почечного клиренса для официального фармакологического дозирования лекарств (FDA/EMA инструкции большинства препаратов нормируются по Cockcroft-Gault, а не по CKD-EPI).
* **Базовая формула Cockcroft-Gault:**
  $$\text{CrCl (мл/мин)} = \frac{(140 - \text{Возраст}) \times \text{Масса тела (кг)}}{72 \times S_{cr}\text{ (мг/дл)}} \times [0.85 \text{ if Female}]$$
* **Критический клинический нюанс при ожирении:**
  Использование реальной массы тела (например, 140–160 кг) приводит к **псевдогиперфильтрации** (расчетный клиренс может получиться $> 200\text{ мл/мин}$), что при дозировании антикоагулянтов или антибиотиков приведет к токсической передозировке.
  * Идеальная масса тела по Devine (IBW):
    $$\text{IBW}_{\text{male}} = 50.0 + 0.9055 \times (\text{Рост}_{\text{см}} - 152.4)$$
    $$\text{IBW}_{\text{female}} = 45.5 + 0.9055 \times (\text{Рост}_{\text{см}} - 152.4)$$
  * Скорректированная масса тела (Adjusted Body Weight, ABW):
    $$\text{ABW} = \text{IBW} + 0.4 \times (\text{Фактическая масса} - \text{IBW})$$
  * **Правило:** Если фактический вес превышает $1.2 \times \text{IBW}$, в Cockcroft-Gault подставляется строго **ABW**.

#### 5. Метаболический возраст (Metabolic Age)
* **Концепция:** Разница между реальным возрастом и возрастом популяции с аналогичным уровнем базального расхода энергии (BMR).
* **Модель расчета:** Сопоставление фактического BMR (рассчитанного по Katch-McArdle с учетом измеренной биоимпедансом безжировой массы FFM) с регрессионной медианой когорты соответствующего пола и возраста. При росте мышечной массы и снижении висцерального жира метаболический возраст снижается ниже паспортного.

#### 6. Дополнительные атерогенные индексы и eAG
* **Non-HDL холестерин:** $\text{Non-HDL} = \text{Общий холестерин} - \text{HDL}$ (целевой уровень $< 2.6\text{ ммоль/л}$ при наличии факторов риска).
* **TG / HDL Ratio:** Суррогатный маркер доли мелких плотных окисленных липопротеинов низкой плотности (норма $< 1.3$ в ммоль/л; $> 2.0$ — высокий риск ишемической болезни сердца).
* **Расчетный средний сахар eAG (ADAG Study):**
  $$\text{eAG (ммоль/л)} = 1.59 \times \text{HbA1c (\%)} - 2.59$$
  $$\text{eAG (мг/дл)} = 28.7 \times \text{HbA1c (\%)} - 46.7$$

## 3. Архитектурные паттерны ИИ-агентов в медицине

### 3.1. Dual-System Architecture: Разделение детерминированных вычислений и LLM

В доказательной медицине и метаболическом инжиниринге действует строгий постулат: **LLM никогда не считает числа и не принимает пороговых решений в уме**.

```
                ПОЛЬЗОВАТЕЛЬ (Telegram / Web)
                              │
                              ▼
   ┌──────────────────────────────────────────────────────┐
   │        КОНТУР 1: Semantic Orchestrator (LLM)         │
   │  • NLU: извлечение интента и параметров               │
   │  • Генерация Tool Call:                              │
   │    call_tool("calculate_biomarkers", {...})          │
   └──────────────────────────┬───────────────────────────┘
                              │  Pydantic Strict Validation
                              ▼
   ┌──────────────────────────────────────────────────────┐
   │       КОНТУР 2: Deterministic Core (Python)          │
   │  • Валидация диапазонов и единиц измерения           │
   │  • IEEE-754 / Decimal вычисления без округлений      │
   │  • Применение физиологических guardrails (полы)      │
   │  • Атомарная запись в SQLite (Source of Truth)       │
   └──────────────────────────┬───────────────────────────┘
                              │  Детерминированный JSON-результат
                              ▼
   ┌──────────────────────────────────────────────────────┐
   │        КОНТУР 1: Semantic Orchestrator (LLM)         │
   │  • Синтез ответа на естественном языке               │
   │  • Клиническое объяснение полученных статусов         │
   │  • Запрет на ввод новых цифр, отсутствующих в ответе │
   └──────────────────────────────────────────────────────┘
```

1. **System 1 (LLM Semantic Core):** Парсит неструктурированный текст пользователя («утром сахар был 5.6, съел 2 яйца и тост»), сопоставляет слоты, вызывает соответствующие зарегистрированные инструменты (Tool Calling) и переводит сухой JSON ответа ядра в поддерживающий, эмпатичный диалог.
2. **System 2 (Deterministic Execution Engine):** Написан на чистом Python с Pydantic-схемами. Обеспечивает 100% воспроизводимость, проверяет границы безопасности (полы калорий, минимальный белок, маркеры риска) и сохраняет факты в базу данных SQLite (WAL-mode).

### 3.2. Почему LLM категорически нельзя доверять расчет калорий и дозировок напрямую

1. **Природа токенизации (BPE Tokenization):** Языковые модели оперируют не разрядами чисел (единицы, десятки, сотни), а статистическими субсловными токенами. Число `1450` может быть одним токеном, а `1451` — двумя токенами (`145` и `1`). Сложение или деление таких токенов — это статистическая генерация вероятного продолжения строки, а не выполнение арифметической инструкции в АЛУ процессора.
2. **Галлюцинации коэффициентов и констант:** LLM регулярно подменяет константы. Например:
   * Путает делитель 22.5 и 405 в HOMA-IR при анализе глюкозы в мг/дл, получая 18-кратную ошибку.
   * Путает слагаемое для пола в формуле Mifflin-St Jeor ($+5$ для мужчин, $-161$ для женщин), занижая BMR мужчины на 166 ккал.
3. **Кумулятивная ошибка суммирования:** При подсчете суточного рациона по отдельным приемам пищи погрешность LLM при прямом суммировании накапливается и достигает $15 - 30\%$. При планируемом дефиците 400 ккал ошибка в 300 ккал полностью уничтожает дефицит либо загоняет пользователя в гипокалорийный шок.
4. **Летальные риски в фармакотерапии:** Ошибка в одну цифру или запятую в расчете клиренса почек или дозировки тирзепатида/семаглутида/инсулина может вызвать фатальную гипогликемию, острый панкреатит или почечную недостаточность.
5. **Невоспроизводимость:** При ненулевой температуре сэмплирования один и тот же запрос выдает разные значения, что противоречит стандартам валидации медицинского ПО (IEC 62304 / SaMD).

## 4. Системы Guardrails для медицинских агентов

### 4.1. Сравнительный анализ систем валидации

* **NeMo Guardrails (NVIDIA):**
  * Использует декларативный язык Colang.
  * Разделяет барьеры на: Input Rails (фильтрация джейлбрейков, инъекций, триггеров вреда), Dialog Rails (направление диалога строго по протоколу), Output Rails (верификация фактов, блокировка назначения рецептурных препаратов), Topical Rails (блокировка оффтопика).
  * *Минус для локального VPS:* Высокая задержка (latency) и потребление ресурсов — требует дополнительных вызовов LLM или локальных эмбеддингов.
* **Guardrails AI:**
  * Построен на спецификациях RAIL (XML/JSON) и интеграции с Pydantic.
  * Механизм `re-ask`: если выход LLM не прошел валидатор (например, `is_valid_range` или `detect_hallucination`), библиотека автоматически делает повторный запрос к LLM с системной подсказкой об ошибке.
  * *Минус для локального VPS:* Хаб валидаторов перегружен тяжелыми зависимостями (PyTorch, transformers, spacy), несовместимыми с 1 GB RAM.
* **Instructor (Jason Liu):**
  * Легковесный инструмент поверх Pydantic V2 для структурированного вывода (Function / Structured Outputs).
  * Нативные `@field_validator` и `@model_validator`. Встроенный retry-loop передает трассировку валидации Pydantic обратно в модель, которая исправляет некорректные поля.
  * Идеален для надежного извлечения сущностей без раздувания зависимостей.
* **Custom Determinism (Архитектура Health Agent System):**
  * Жесткие assert'ы и защитные функции в доменном ядре (`health_core/guards.py`).
  * Полная независимость от внешних ML-библиотек, мгновенное исполнение, нулевой оверхед по RAM.

### 4.2. 5-уровневая модель автономности медицинского агента

| Уровень | Категория | Область действия | Требования к контролю человека |
|---|---|---|---|
| **Level 1** | **Wellness & Энергия** | Подсчет базового BMR, трекинг веса, вода, сон | Полностью автоматический (детерминированный) |
| **Level 2** | **Клинический скрининг** | Расчет HOMA-IR, TyG, eGFR, соотношений липидов | Автоматический расчет с предупреждением: «Требуется интерпретация врача» |
| **Level 3** | **Фармакотерапия** | Моделирование полувыведения GLP-1, тайминг инъекций | Напоминание по факту назначения врача; **запрет на самостоятельное изменение дозы** |
| **Level 4** | **Высокорисковые состояния** | Острый дефицит, глубокая саркопения, падение СКФ | Жесткий стоп системы: принудительный вывод из дефицита (рефид) |
| **Level 5** | **Emergency Triage** | Загрудинная боль, признаки инсульта, суицидальные маркеры | Немедленная блокировка диалога и вывод номеров экстренных служб |

## 5. Опыт мультиагентных систем в здравоохранении

### 5.1. Анализ ведущих фреймворков

1. **Med-Agent:**
   * Мультиагентная архитектура клинического рассуждения.
   * Разделение ролей:
     * *Диагност (Primary Diagnostician)* — формулирует гипотезы по жалобам.
     * *Агент назначения исследований (Test Selector)* — определяет минимально необходимый диагностический поиск, исключая гипердиагностику.
     * *Верификатор/Критик (Reviewer Agent)* — анализирует противоречия и когнитивные искажения (например, предвзятость подтверждения).
   * Результат: повышение точности на 20% по сравнению со стандартным одиночным промптингом.

2. **AgentClinic (Stanford / Harvard / MIT):**
   * Первая эталонная среда симуляции закрытого клинического приема.
   * Участники:
     * `Doctor Agent` — проводит сбор анамнеза, физикальный осмотр, формирует диагноз и терапию.
     * `Patient Agent` — наделен реалистичным фенотипом, скрытым анамнезом и психоэмоциональными особенностями.
     * `Measurement Environment` — эмулирует лабораторию и диагностику (инструментальные тесты выдаются с виртуальной задержкой и стоимостью).
   * Ключевой вывод исследования: одиночные агенты страдают **преждевременным закрытием диагноза (premature closure)** в 42% случаев — они ставят диагноз по первому симптому, не спросив про аллергии, семейный анамнез или сопутствующие препараты. Мультиагентная система устраняет эту проблему.

3. **Clinical-Agent / Simulated Multi-Specialist Board (Врачебный консилиум):**
   * Моделирование профильных специалистов: Эндокринолог, Кардиолог, Спортивный врач, Фармаколог.
   * Мета-агент (**Chief Medical Officer**) производит деконфликтинг: если эндокринолог назначил препарат, снижающий аппетит, а спортивный врач увеличил тренировочный объем, консилиум балансирует нагрузку во избежание гипогликемии.

### 5.2. Адаптация мультиагентного опыта для локального Health Agent System

Для персонального ассистента запуск нескольких параллельных нейросетей на одном сервере невозможен из-за лимитов памяти (1 GB RAM) и сетевых квот.

**Архитектурное решение:** *Детерминированный консилиум модулей (Specialist Guard Pipeline)*.
Единый оркестратор последовательно прогоняет контекст через независимые детерминированные фильтры:
* `PharmaKineticModule` — отслеживает кривую концентрации тирзепатида.
* `KneeInjuryFilter` — блокирует любые рекомендации осевых и ударных нагрузок на травмированный сустав (ПКС).
* `MetabolicFloorGuard` — проверяет, что калораж не падает ниже BMR.
* `BingeTriadPredictor` — оценивает накопленный стресс и риск переедания.

### 6.1. Сравнение спецификаций: Anthropic MCP vs Antigravity Skills vs Hermes Registry

| Параметр | **Anthropic MCP (Model Context Protocol)** | **Antigravity Skills (Google/Gemini)** | **Hermes Agent / In-Process Registry** |
|---|---|---|---|
| **Транспорт** | JSON-RPC over stdio / SSE | CLI манифесты, markdown-контекст | Прямой async Python callable в памяти |
| **Изоляция** | Отдельный OS-процесс | Внутриконтекстная / CLI подпроцесс | Единое адресное пространство процесса |
| **RAM оверхед** | +30–60 МБ на каждый сервер | Минимальный (в промпте) | **0 МБ дополнительно (максимальная экономия)** |
| **Latency** | 5–30 мс на вызов (сериализация) | Зависит от CLI рантайма | **< 0.1 мс (мгновенно)** |
| **Экосистема** | Claude Desktop, Claude Code, Cursor, Zed | Gemini CLI, Antigravity Agent Platform | Telegram-боты на aiogram, автономные демоны |
| **Вердикт для проекта** | Отлично для отладки через Claude Code | Отлично для документации и промптов | **Основной рантайм для VPS (1 vCPU / 1 GB RAM)** |

## 8. Приоритетный роадмап внедрения в Health Agent System

```
┌────────────────────────────────────────────────────────────────────────┐
│                        ПРИОРИТЕТЫ ВНЕДРЕНИЯ                            │
├────────────────────────────────┬───────────────────────────────────────┤
│ Спринт 1: Неотложные фиксы     │ 1. Инверсия знака в adaptive_tdee    │
│ (Безопасность ядра)            │ 2. Исправление знака в LBM_RATIO     │
│                                │ 3. TCX-парсер: сброс флага in_lap    │
├────────────────────────────────┼───────────────────────────────────────┤
│ Спринт 2: Топ-1 Мета-скилл     │ Binge Risk Triad (cron + notify.py)   │
│ (Проактивная защита от срывов) │ Накопленный дефицит + сон + белок     │
├────────────────────────────────┼───────────────────────────────────────┤
│ Спринт 3: Фармакокинетика      │ GLP-1 Kinetics (Тирзепатид)           │
│ (Тайминг рефидов и аппетита)   │ Экспоненциальный распад C(t)          │
├────────────────────────────────┼───────────────────────────────────────┤
│ Спринт 4: Лабораторный модуль  │ log_labs (HOMA-IR, TyG, eGFR, Non-HDL)│
│ (Объективизация метаболизма)   │ Чистый Python, текстовый ввод без OCR │
├────────────────────────────────┼───────────────────────────────────────┤
│ Категорический отказ (OOM-риск)│ Локальный Whisper, PaddleOCR, Nougat  │
└────────────────────────────────┴───────────────────────────────────────┘
```

### Главные архитектурные рекомендации:
1. **Никаких тяжелых нейросетевых моделей локально:** Любой локальный OCR (PaddleOCR, Nougat) или STT (Whisper) мгновенно вызовет OOM на 1 GB RAM. Ввод лабораторных данных должен производиться **только текстом** через диалог или структурированный шаблон.
2. **Сериализация записи в SQLite:** В `bot/llm.py` следует исключить параллельное исполнение записывающих инструментов через `asyncio.gather`, используя последовательный вызов либо глобальный `asyncio.Lock()` для предотвращения ошибки `database is locked`.
3. **Хранение чистой логики в `health_core/`:** Все формулы должны жить в `health_core/`, оставаясь доступными как боту, так и cron-скриптам в `scripts/` и модульным тестам.
