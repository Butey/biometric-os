# Plan

## Overview
Develop a rigorous implementation and validation plan for the Metabolic Contour Health Agent System, focusing on a dual-system architecture that separates LLM-driven empathetic coaching from deterministic, Python-based metabolic mathematics. The plan prioritizes strict hardware constraints (1 vCPU, 1 GB RAM), clinical safety for a single Tirzepatide patient, and immediate correction of critical formula bugs to ensure maximum fat loss and Lean Body Mass (LBM) preservation.

## Scope
- In: Deterministic metabolic math implementation (Hall, Pontzer, Alpert, MATADOR) in Python; Pydantic V2 validation; SQLite database configuration; integration of open-source engines (PMC, PK, PuLP); behavioral psychology telemetry (CBT-E, ACT); core bug fixes.
- Out: Multi-user support; local heavy ML/DL deployment (Whisper, Torch, etc.); non-GLP-1 clinical pathways; LLM-based mathematical reasoning.

## Testing Strategy
- Unit Testing: Pytest suite for all deterministic metabolic formulas (Hall, Pontzer, Alpert, MATADOR) to ensure exact values.
- Property-Based Testing: Use `hypothesis` to fuzz Pydantic V2 schemas, ensuring no mathematically impossible states (e.g., negative fat mass) pass validation.
- Resource Profiling: Run load tests in a Docker container strictly limited to 1 vCPU and 1 GB RAM (`--cpus=1 -m 1g`) to verify the absence of OOM kills.
- Dual-System Testing: Mock the LLM responses to verify that hallucinatory math in tool arguments is caught and rejected by Pydantic.

## Risks
- **OOM Errors during PuLP Optimization:** Complex mathematical optimization could spike memory usage above the 1 GB limit. *Mitigation:* Implement strict solver timeouts and aggressive Python garbage collection after optimization runs.
- **LLM Prompt Injection/Bypass:** The LLM might attempt to bypass tool calling and output unauthorized advice. *Mitigation:* System prompt enforcement and strict output parsing that redacts unsolicited mathematical claims.
- **Self-critique:** The plan heavily relies on Pydantic V2 for runtime validation, which introduces CPU overhead. On a 1 vCPU machine, parsing large payloads of historical telemetry could cause unacceptable latency or block the event loop.
- **Self-critique:** The plan lacks a dedicated fallback mechanism if the open-source compute engines (PMC/PK/PuLP) fail to find a feasible solution for the target macros (e.g., 1.6-2.2 g/kg FFM) under extreme caloric deficits, which could paralyze the agent's coaching logic.

## Rollback Plan
- Codebase: Maintain semantic versioning via Git tags. In case of critical failure, revert the active container image to the previous tag.
- Database: Perform an automated SQLite dump (`.sqlite.bak`) prior to any schema migration or engine deployment. Rollback involves replacing the `.sqlite` file with the backup and restarting the service.

## Edge Cases
- Rapid water weight fluctuations masking LBM preservation, triggering false positive LBM drift alerts.
- Unusually high protein requirements (e.g., > 2.2 g/kg FFM) that mathematically conflict with Alpert's maximum fat transfer limits during deep caloric deficits.
- The user inputs non-standard metric/imperial units that bypass NLU normalization.
- Total loss of internet connectivity preventing LLM API calls, requiring local fallback caching of recent adherence protocols.
