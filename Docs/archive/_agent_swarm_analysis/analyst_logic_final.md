# Analyst-Logic — финальный отчёт (верификация + продолжение)

Все находки ниже проверены непосредственным чтением актуального исходного кода
(не по памяти и не по прежнему отчёту). Номера строк указаны на момент чтения
файлов в ходе этого прогона.

## Сводное резюме (по убыванию критичности)

1. **Инвертирован знак в adaptive_tdee** (`health_core/energy.py:201`) — система
   занижает расчётный расход энергии именно тогда, когда человек успешно
   худеет, и вместо повышения TDEE опускает его ниже фактического — прямой
   путь к спирали урезания калорий ниже BMR.
2. **Гардрейлы LBM_RATIO/LBM_DRIFT используют `abs()` без проверки направления**
   (`health_core/guards.py:74, 89, 122`) — критический алерт «потеря мышц»
   срабатывает и на здоровом наборе мышечной массы, и на рекомпозиции тела.
3. **`adaptive_tdee` не параметризован датой** (`health_core/energy.py:173, 297`)
   — при ретроспективном пересчёте целей за прошлые дни в них записывается
   СЕГОДНЯШНИЙ метаболизм, что ломает историю адаптации и делает пайплайн
   неидемпотентным.
4. **Гардрейл FFMI_FLOOR слеп к полу** (`health_core/guards.py:133-152`,
   порог `config.yaml:86` = 19.0 кг/м² один на всех) — для подавляющего
   большинства женщин (типичный FFMI 14-17) этот «критический» алерт о
   саркопении будет висеть перманентно, обесценивая сигнал; система либо
   не различает реальную проблему на этом канале для женщин вовсе, либо
   постоянно эскалирует ложную тревогу.
5. **Несогласованность macro-минимума: белок+жир могут физически не влезать
   в цель по калориям** (`health_core/energy.py:106-148, 382-392`) —
   `kcal_floor` подпирает пол минимумом, посчитанным по `fat_pct_min` (0.20),
   а фактические граммы жира в `daily_target` считаются по номинальному
   `fat_pct` (0.30) — на полу по причине `macro_minimum` итоговая сумма
   ккал из белка и жира численно превышает `kcal_target`.
6. **Неснижаемый жир в forecast.py задан одной константой без учёта пола**
   (`health_core/forecast.py:108-110, 231`, `ESSENTIAL_FAT_PCT = 0.05`) —
   комментарий в самом файле говорит «неснижаемый жир У МУЖЧИН», но
   применяется к обоим полам одинаково; для женщин порог остановки
   симуляции биологически занижен.
7. **LIPID_GUARD молчит именно в самом опасном случае** (`health_core/guards.py:293-294`)
   — приём препарата совсем без еды рядом (`window["n"] == 0`) не проверяется
   вовсе. Пограничная находка: это согласуется с общей философией модуля
   «нет данных → гард не судит», но именно здесь «нет данных» неотличимо от
   «принял натощак», а это ровно тот сценарий, ради которого гард существует.
8. **UNDEREATING считает незавершённый «сегодня» полноценным днём недоедания**
   (`health_core/guards.py:157-178`) — окно в `days` дней включает `i=0`
   (сегодня), и если человек с утра съел только завтрак, день тривиально
   попадает «ниже 80% цели», раздувая счётчик подряд идущих дней раньше
   срока.

## Детальные находки

### 1. `health_core/energy.py:201` — sign error в `adaptive_tdee`

```python
return mean_intake + (delta_weight * 7700 / window_days)
```

Энергетический баланс за окно: `Δзапас_энергии = intake·N − TDEE·N`, и
`Δзапас_энергии = delta_weight · 7700` (набор массы = накопление энергии,
потеря = её расход сверх прихода). Отсюда:

```
delta_weight · 7700 = N·mean_intake − N·TDEE
TDEE = mean_intake − delta_weight · 7700 / N
```

Знак в коде — плюс, а должен быть минус. При потере веса (`delta_weight < 0`)
реальный TDEE ВЫШЕ среднего прихода (человек ел меньше, чем тратил, — отсюда
и похудел), а формула вычитает из intake ещё и модуль дельты, занижая TDEE
вдвойне. Пример: ели 2000 ккал/сут, потеряли 1 кг за 14 дней
(`delta_weight = -1`): правильный TDEE = 2000 − (-1·7700/14) = 2550 ккал;
код выдаёт 2000 + (-550) = 1450 ккал. Разница 1100 ккал на калибровочной базе
— система решит, что человеку требуется урезать калораж куда сильнее, чем
нужно на самом деле, хотя он и так уже в дефиците и худеет. Симметрично при
наборе веса формула завышает TDEE.

**Медицинская опасность.** Раз в дефиците и так, а система дополнительно
занижает базу — цель по калориям на следующем цикле уедет ниже безопасного
`kcal_floor` только за счёт того, что `full_tdee` (шаг 1) занижен; клампы в
`daily_target` спасут абсолютное дно, но динамика «чем успешнее худеешь, тем
сильнее тебя режут» останется и будет провоцировать срывы, гипогликемию,
чрезмерный голод.

**Фикс:** заменить `+` на `-`:
```python
return mean_intake - (delta_weight * 7700 / window_days)
```

### 2. `health_core/guards.py:74, 89, 122` — LBM_RATIO / LBM_DRIFT игнорируют направление

`_lean_loss_ratio` (строка 74):
```python
return abs(d_lean) / abs(d_weight), d_weight, d_lean, len(rows)
```
`check_lbm_ratio` (строка 89) и `check_lbm_drift` (строка 122) одинаково:
```python
if ratio > threshold:
```
— оба гарда судят только по модулю отношения, не глядя на знаки `d_weight` и
`d_lean`, при том что оба знака у функции уже возвращены и доступны.

**Опасность.** Рассмотрим кейсы:
- Профицит + набор мышц (`d_weight > 0`, `d_lean > 0`, рост FFM опережает рост
  жировой массы, что нормально на старте силового тренинга или на возврате
  после диеты): при небольшой прибавке общей массы и заметном приросте FFM
  `ratio` легко перевалит за `lbm_ratio_threshold = 0.15`. Система выдаст
  критический алерт «Доля тощей массы в потере... выше порога» — про потерю,
  которой не было, а был набор.
- Рекомпозиция (`d_weight < 0`, `d_lean > 0` — жир уходит, мышцы растут):
  тот же ложный критический алерт на объективно лучшем из возможных исходов.

Порог `lbm_ratio_threshold=0.15` и `lbm_drift_threshold=0.20` (config.yaml) —
оба «critical» по `GUARD_DEFINITIONS`, то есть это не тихое предупреждение, а
самая громкая эскалация в системе, отправляемая при физиологически
благоприятном результате. Постоянные ложные критические алерты приводят к
эффекту «мальчик кричал волк»: когда однажды случится настоящая потеря мышц,
пользователь скорее проигнорирует и это сообщение.

**Уточнение к фиксу.** Предложение «просто требовать `d_weight<0 and d_lean<0`»
(из прежнего черновика) недостаточно: оно также ПРОПУСТИТ действительно
опасный случай — набор веса за счёт жира при ОДНОВРЕМЕННОЙ потере мышц
(`d_weight > 0`, `d_lean < 0`, саркопеническое ожирение на профиците). Гард
должен реагировать на сам факт потери тощей массы, а не на знак изменения
общего веса:

```python
if d_lean >= 0:
    return None  # тощая масса не падает — гарду не о чем судить
ratio = abs(d_lean) / abs(d_weight) if d_weight != 0 else float("inf")
...
if ratio > threshold:
    ...
```
т.е. условие должно быть `d_lean < 0`, независимо от `d_weight`.

### 3. `health_core/energy.py:173, 297` — `adaptive_tdee` не принимает дату

```python
def adaptive_tdee(conn: sqlite3.Connection, user_id: int, window_days: int = 14) -> float | None:
    ...
    end = local_now().date()          # строка 173 — всегда "сейчас"
```
```python
adaptive = adaptive_tdee(conn, user_id)   # строка 297, daily_target — без даты
```

`daily_target(conn, user_id, date)` принимает произвольный `date` (для
ретроактивного пересчёта целей задним числом), но внутри дёргает
`adaptive_tdee` без передачи этого `date` — окно 14 дней всегда отсчитывается
от реального «сегодня» сервера, а не от `date`, для которого считается цель.

**Опасность.** Любой ретроспективный пересчёт (миграция, восстановление
истории, бэктест) за прошлый месяц запишет в `daily_targets` за прошлые числа
метаболизм СЕГОДНЯШНЕГО дня, а не тот, что был актуален тогда. Это ломает
идемпотентность (`daily_target(conn, uid, "2026-08-20")`, вызванный сегодня и
через месяц, даст разные `kcal_target` для одной и той же исторической даты)
и обесценивает историю адаптации метаболизма в БД — по ней потом строятся
графики/тренды в `report.py`.

**Фикс:**
```python
def adaptive_tdee(conn, user_id, window_days=14, date: str | None = None) -> float | None:
    end = date.fromisoformat(date[:10]) if date else local_now().date()
    ...
```
и в `daily_target`: `adaptive = adaptive_tdee(conn, user_id, date=date)`.
Также стоит пробросить `date` в `forecast.py:319` и `report.py:350`
(`trends()`), которые вызывают `adaptive_tdee` без даты для отображения
«текущего» TDEE — там это осмысленно (нужен именно сегодняшний), но явная
передача `date=local_now().date().isoformat()` избавит от скрытой зависимости
от `local_now()` внутри самой функции и упростит тестирование.

### 4. `health_core/energy.py:106-148, 382-392` — macro-минимум считается не по тому `fat_pct`, что реально идёт в цель

`kcal_floor` (106-148) при недостатке жировой массы для безопасного дефицита
подпирает пол через `macro_minimum_kcal` (92-103):
```python
pct_min = t.get("fat_pct_min", 0.20)
return t["protein_g"] * 4 / (1 - pct_min)
```
т.е. минимально допустимый калораж считается исходя из МИНИМАЛЬНОЙ доли жира
20%. Но реальные граммы жира, которые попадут в выданную цель, считаются в
`daily_target` (386-387) по НОМИНАЛЬНОЙ доле:
```python
fat_pct = targets.get("fat_pct")             # 0.30 по умолчанию (config.yaml)
fat_g = round(kcal * fat_pct / 9, 1) if fat_pct else None
```
а белок (`protein_g`, строка 383) вообще не зависит от `kcal` — это
`1.8 г/кг FFM` (`config.py:117`), фиксированная величина.

**Численный пример.** FFM = 70 кг → `protein_g = 1.8·70 = 126` г → белковых
ккал 504. `macro_minimum_kcal = 126·4 / (1 − 0.20) = 630` ккал — именно это
число `kcal_floor` подставит как пол, если сработает ветка
`floor_reason == "macro_minimum"`. При `kcal = 630`:
`fat_g = 630·0.30/9 = 21` г → жировых ккал 189.
`protein_kcal + fat_kcal = 504 + 189 = 693 ккал > 630 ккал` — то есть
белок и жир из НЕОТКЛОНИМОЙ («это же минимум!») цели уже физически не влезают
в саму цель по калориям на 63 ккал (~10%), а `carbs_g` при этом дополнительно
клампится в 0 (`max(0.0, kcal - protein_g*4 - fat_g*9)`, строка 392) — то есть
план невозможно выполнить в трекере калорий: если съесть ровно прописанные
граммы белка и жира, итоговый факт превысит `kcal_target`, хотя углеводов в
плане формально ноль.

**Причина.** `macro_minimum_kcal` строился ИМЕННО чтобы гарантировать, что
белок с минимальным жиром влезают в calorie floor — но `daily_target` считает
итоговые граммы жира не по этому же минимуму, а по номинальной, более высокой
доле. Гарантия рвётся ровно там, где она нужнее всего (человек на самом низком
безопасном калораже).

**Фикс.** Либо (а) при формировании итоговых `fat_g`/`carbs_g` в
`daily_target` использовать `min(fat_pct, ...)`, снижая долю жира до
`fat_pct_min`, когда `kcal` близок к `macro_minimum`/`kcal_floor`
(`floor_reason == "macro_minimum"`), либо (б) заново проверить после расчёта
`fat_g`, что `protein_g*4 + fat_g*9 <= kcal`, и если нет — увеличить `kcal` до
факта `protein_g*4/(1-fat_pct)` вместо номинального `fat_pct_min`-минимума в
`kcal_floor`. Вариант (б) точнее: `macro_minimum_kcal` должен считаться по
тому же `fat_pct`, что реально уйдёт в `fat_g`, а не по отдельной константе
`fat_pct_min`.

### 5. `health_core/guards.py:133-152` — FFMI_FLOOR не учитывает пол

```python
def check_ffmi_floor(conn, user_id):
    ...
    ffmi = row["ffm_kg"] / (height_m ** 2)
    threshold = cfg["ffmi_floor"]          # config.yaml: 19.0 — одно число на всех
    if ffmi < threshold:
        return _alert("FFMI_FLOOR", "critical", ...)
```
Функция ни разу не читает `users.sex`, хотя таблица `users` эту колонку имеет
и используется в соседних гардах (`check_whr`, строка 313-316, где мужской и
женский пороги разведены явно). `GUARD_DEFINITIONS["FFMI_FLOOR"]["rationale"]`
(строка 623) прямо говорит про порог «для взрослого мужчины», но код
применяет его и к женщинам.

**Опасность.** Естественный FFMI у нетренированных/умеренно тренированных
женщин обычно 14-17 кг/м² — заметно ниже мужского референса 19-20.
Практический эффект: для абсолютного большинства пользовательниц-женщин этот
«критический» гард будет включён почти постоянно, независимо от реальной
динамики их мышечной массы, потому что порог для них биологически некорректен.
Постоянный ложный `critical`-алерт «клиническая саркопения» либо игнорируется
(теряется реальный сигнал при действительной потере мышц у женщин, раз алерт
и так всегда горит), либо провоцирует необоснованную остановку дефицита
(`GUARD_DEFINITIONS["FFMI_FLOOR"]["action"]`: «Полная остановка дефицита
калорий») там, где в этом нет медицинской необходимости.

**Фикс:** завести раздельные пороги (`ffmi_floor_m`, `ffmi_floor_f` в
`config.yaml`, аналогично `whr_male_max`/`whr_female_max`) и выбирать по
`users.sex`, как это уже сделано в `check_whr`.

### 6. `health_core/forecast.py:108-110, 231` — `ESSENTIAL_FAT_PCT` не зависит от пола

```python
# Неснижаемый жир у мужчин — около 3-5% массы. Ниже этой границы симуляция
# обрывается...
ESSENTIAL_FAT_PCT = 0.05
```
и в `_simulate` (строка 231):
```python
if fat_kg <= weight_kg * ESSENTIAL_FAT_PCT:
    truncated = day + 1
```
`sex` передаётся в `_simulate` (используется только для `bmr_mifflin`), но
предохранитель обрыва симуляции при исчерпании жирового депо игнорирует пол
полностью, хотя сам docstring честно называет 5% нормой для мужчин
(общепринятая физиологическая норма неснижаемого жира у женщин — порядка
10-13%, вдвое-втрое выше).

**Опасность.** Для пользовательниц-женщин посуточная симуляция (`project`,
`reach`) продолжит «безопасно» снижать жировую массу вплоть до 5% от веса —
то есть модель покажет и не остановит траекторию похудения на уровне,
физиологически недостижимом и опасном для женщины (аменорея, потеря
костной массы и т.д.), прежде чем предохранитель хоть как-то сработает.
Дальше в `_simulate` правило Форбса при почти пустом жировом депо резко
увеличивает долю тощей массы в «потере» (см. комментарий в docstring модуля,
строки 63-65) — то есть по мере приближения к неверному порогу траектория
начинает всё сильнее (и неправдоподобно) съедать мышцы, и это будет
представлено пользователю как «прогноз», прежде чем модель наконец
остановится на биологически неверном пороге.

**Фикс:** сделать порог зависимым от `sex` — например,
`ESSENTIAL_FAT_PCT_M = 0.05`, `ESSENTIAL_FAT_PCT_F = 0.11` (или вынести в
`config.yaml` под `forecast:`), и выбирать по полу внутри `_simulate`/`project`.

### 7. `health_core/guards.py:293-294` — LIPID_GUARD молчит при полном отсутствии еды рядом с приёмом (пограничная находка)

```python
if window["n"] == 0:
    continue  # рядом ничего не ели — не судим по нулю
```
**Наблюдение.** Это поведение СОГЛАСУЕТСЯ с общей и явно заявленной философией
модуля (docstring `guards.py:1-6`: «Гардрейл без данных не срабатывает
никогда») и с тем же паттерном в `check_undereating` (строка 173-174,
«не путаем молчание с недоеданием»). В этом смысле это не одиночная ошибка
разработчика, а последовательно применённый принцип.

**Почему всё равно стоит внимания.** Для остальных гардов «нет записи» и
«действие не выполнено» — разные вещи (не поел ≠ не ел вовсе). Но для
LIPID_GUARD именно отсутствие еды рядом с приёмом ORAL-препарата и есть
целевой опасный случай: жирорастворимый препарат, принятый строго натощак,
всасывается хуже всего. Трактовка «нет записи еды = не судим» здесь
систематически исключает из проверки самый рискованный сценарий (принял
таблетку и правда ничего не ел), путая его с «пользователь просто не
залогировал перекус». В отличие от UNDEREATING (где ложное срабатывание было
бы хуже, потому что там речь о статистике за несколько дней, и один
пропущенный лог не должен клеймить систему), здесь единичный необнаруженный
случай — это единичная пропущенная доза без достаточного всасывания,
последствия которой не сглаживаются на длинном окне.

**Рекомендация:** не убирать принцип целиком, а завести отдельный, более
мягкий сигнал (severity `info`/`warning`, отдельный код, например
`LIPID_GUARD_NO_FOOD`) на случай `window["n"] == 0`, текстуально отличный от
«жиров мало» — «рядом с приёмом препарата не залогировано ни одного приёма
пищи»; это даст пользователю действие (залогировать факт еды или подтвердить
приём натощак) без ложного обвинения в недостатке жиров там, где еда просто
не записана.

### 8. `health_core/guards.py:157-178` — UNDEREATING засчитывает незавершённый «сегодняшний» день

```python
def check_undereating(conn, user_id):
    days, ratio = cfg["undereating_days"], cfg["undereating_ratio"]
    today = _now().date()
    for i in range(days):                 # i=0 => d=today
        d = (today - timedelta(days=i)).isoformat()
        ...
        if intake["n"] == 0:
            return None                    # не путаем молчание с недоеданием
        if not intake["kcal"] < ratio * target["kcal_target"]:
            return None
    return _alert("UNDEREATING", ...)
```
Цикл включает `i=0` — то есть текущий, ещё не закончившийся календарный день.
Если у пользователя уже есть `daily_targets` на сегодня и он успел
залогировать хотя бы один приём пищи (`intake["n"] > 0`, иначе — ранний
`return None`), но пока съел меньше `ratio·kcal_target` просто потому, что
сейчас, скажем, 10 утра и был только завтрак — это тривиально даёт
`intake["kcal"] < ratio*target`, и день засчитывается как «недоеденный»,
хотя до конца суток ещё далеко.

**Эффект.** Если оба предыдущих дня также попадают под критерий (что вполне
возможно и без реального хронического недоедания — например, у человека
просто плотный поздний ужин по привычке), алерт «Приём пищи ниже 80% цели 3
дня подряд» способен сработать в середине дня, до того как пользователь
физически успел доесть до нормы. Это ложное срабатывание `warning`-уровня
(не критическое, но всё же лишний, преждевременный совет «доешьте калорий» в
момент, когда день не закончен).

**Фикс:** исключить текущий день из окна учёта (начинать цикл с `i=1`,
то есть считать «подряд идущих ЗАВЕРШЁННЫХ дней»), либо проверять `today`
только после какого-то позднего часа (например, после 21:00, аналогично
`_meal_clause`/вечернему отчёту в `report.py`).
