## 0. Проблема добавления тренировок к суточной цели еды («Eat-Back Calories»)

В модуле `health_core/energy.py` сожжённые на тренировке калории (`_tcx_net`) прибавляются к дневному расходу, из-за чего бот повышает целевую планку калорий на день тренировки.

**Почему это принципиальная ошибка:**
1. **Двойной учёт (Double Counting):** При наличии адаптивного TDEE потеря веса за 14 дней ($-\Delta W \cdot 7700 / 14$) **уже включает** энергозатраты на тренировки. Прибавляя `tcx_net` поверх адаптивной базы, система считает тренировки дважды.
2. **Модель ограниченных энергозатрат (Pontzer Constrained Model):** Организм компенсирует тренировочный расход падением спонтанной бытовой активности (NEAT) на 28–50%. Попытка «доесть» потраченное на тренировке гарантированно уничтожает суточный дефицит.
3. **Завышение датчиками:** Пульсометры и трекеры завышают расход силовой работы на 30–50%.
4. **Качели калоража:** В дни тренировок калораж подскакивает на сотни калорий, а в дни отдыха падает. Организм на GLP-1 терапии нуждается в стабильном, предсказуемом поступлении нутриентов.

*Подробный физиологический и клинический разбор вынесен в файл:* [`02_workout_calories_deep_dive.md`](./02_workout_calories_deep_dive.md).

## 2. Детальное описание и инструкции по исправлению

### Дефект 1: Обрыв адаптивной калибровки при `tdee < bmr_floor`
* **Где:** [`health_core/energy.py:339-341`](file:///opt/webapps/health_agent_system/health_core/energy.py#L339)
* **Анализ:**
  ```python
  tdee = mean_intake - (delta_weight * 7700 / window_days)
  if tdee < bmr_floor(conn, user_id):
      return None, logged_days
  ```
  В реальных данных на 23.09: `mean_intake = 1664`, $\Delta W = -0.7$ кг за 14 дней.
  $\text{TDEE} = 1664 + 385 = 2049$ ккал. Базовый обмен $\text{BMR} = 2168$ ккал.
  Так как $2049 < 2168$ (всего на 5% ниже формулы Katch-McArdle), функция вернула `None`.
  Блендер обнулил адаптивную долю и упал на `steps_est`: **2675 ккал**.
  Расход дня искусственно подскочил на **+626 ккал**.
* **Как исправить:**
  Не отбрасывать в `None`, если TDEE находится в физиологическом коридоре метаболической адаптации (напр. $\ge 0.70 \times \text{BMR}$). Клампить снизу к `bmr_floor`:
  ```python
  bmr = bmr_floor(conn, user_id)
  if tdee < bmr * 0.70:
      return None, logged_days
  tdee = max(tdee, bmr)
  return tdee, logged_days
  ```

### Дефект 2: Двойной счёт тренировок в блендере
* **Где:** [`health_core/energy.py:596-599`](file:///opt/webapps/health_agent_system/health_core/energy.py#L596)
* **Анализ:**
  ```python
  if adaptive_est is not None:
      a = policy.get("blend_adaptive_max_share", 0.6) * logged_days / 14
      parts["adaptive"] = {"estimate": adaptive_est + tcx_net, "share": a}
  ```
  По ADR 0004 тренировочная добавка предусматривалась **только для шагомера**, так как часы не видят упражнения с отягощениями. В адаптивную часть она добавляться не должна.
* **Как исправить:**
  Убрать `+ tcx_net` из адаптивной ветки:
  ```python
  parts["adaptive"] = {"estimate": adaptive_est, "share": a}
  ```

### Дефект 3: `forecast.py` завышает intake из-за неотфильтрованных рефидов
* **Где:** [`health_core/forecast.py:168-177`](file:///opt/webapps/health_agent_system/health_core/forecast.py#L168)
* **Анализ:**
  В `_observed_intake()` средний приход считается простым средним всех дней окна без исключения дат из `refeed_days` и `sick_days`. Из-за этого приход оценивается в 1945 ккал вместо чистых 1800 ккал, и дата достижения вехи 115 кг сдвигается с середины октября на 27 октября.
* **Как исправить:**
  Добавить фильтрацию дат по таблицам `refeed_days` и `sick_days` точно так же, как было сделано в `health_core/energy.py`:
  ```python
  refeed_sick_dates = {r["date"] for r in conn.execute(
      "SELECT date FROM refeed_days WHERE user_id=? AND date BETWEEN ? AND ? "
      "UNION SELECT date FROM sick_days WHERE user_id=? AND date BETWEEN ? AND ?",
      (user_id, start.isoformat(), end.isoformat(), user_id, start.isoformat(), end.isoformat()),
  ).fetchall()}
  values = [r["kcal"] for r in rows if r["kcal"] is not None and r["d"] not in refeed_sick_dates]
  ```

### Дефект 4: Искажение расчёта дефицита и слота завтрака в `check_binge_risk`
* **Где:** [`health_core/guards.py:125-155`](file:///opt/webapps/health_agent_system/health_core/guards.py#L125)
* **Анализ:**
  1. Берётся единичный `tdee` за вчерашний день и применяется ко всем 5 дням подряд: `deficit_sum += tdee - eaten`. Если вчерашний день был искажён или имел тренировку, дефицит умножается на 5 (так возник ложный алерт на дефицит 6481 ккал).
  2. В дни рефида дефицит должен быть 0, а код продолжает вычитать `tdee - eaten`.
  3. Проверка `fl.meal_slot='breakfast'` ложно срабатывает после 12:00, если человек ест без маркировки слотов или на периодическом голодании.
* **Как исправить:**
  Брать фактические суточные цели из `daily_targets` для каждого дня; для дней рефида обнулять дефицит; для завтрака проверять первый приём пищи за день хронологически.

### Дефект 5: Ложный алерт `BMR_FLOOR` при вечернем взвешивании расхода
* **Где:** [`health_core/guards.py:240-270`](file:///opt/webapps/health_agent_system/health_core/guards.py#L240)
* **Анализ:**
  Утренняя цель (2128 ккал) сверяется с вечерним пересчитанным полом (2385 ккал), который вырос за счёт шагов и тренировок.
* **Как исправить:**
  Сохранять `kcal_floor` в строке `daily_targets` в момент утверждения утренней цели и сверять сохранённое значение с сохранённым полом, а не с плавающим вечерним расходом.

### Дефект 6: Вечерние замеры веса искажают сглаженный вес в `energy.py`
* **Где:** [`health_core/energy.py:177-183`](file:///opt/webapps/health_agent_system/health_core/energy.py#L177)
* **Анализ:**
  `_smoothed_weight_kg` не содержит фильтра `time(measured_at) BETWEEN '06:00:00' AND '11:00:00'`, в отличие от `_morning_weights`. Вечерние замеры (с задержкой воды) сдвигают медиану вверх, заставляя код требовать избыточный дефицит.
* **Как исправить:**
  Добавить фильтрацию утренних замеров и группировку по суточным медианам.

### Дефект 7: Прыжок калоража на поддержку при достижении целевого веса
* **Где:** [`health_core/energy.py:469-471`](file:///opt/webapps/health_agent_system/health_core/energy.py#L469)
* **Анализ:**
  Если текущий вес стал $\le$ порога вехи, `_deadline_deficit` возвращает `0.0`. Цель становится равной полному расходу (~2500 ккал). Пока пользователь или бот не переключит веху на следующую, дефицит блокируется.
* **Как исправить:**
  При достижении порога автоматически переключаться на следующую активную веху в очереди (`ORDER BY threshold DESC` для похудения) или удерживать безопасный дефолтный дефицит.

### Дефект 8: 0 дефицита для вех без дедлайна
* **Где:** [`config.yaml:76`](file:///opt/webapps/health_agent_system/config.yaml#L76), [`health_core/energy.py:442`](file:///opt/webapps/health_agent_system/health_core/energy.py#L442)
* **Анализ:**
  Запрос `_active_milestone` отбирает только вехи с `deadline IS NOT NULL`. Если веха задана без срока, код переходит на `default_deficit_kcal`, который равен `0`.
* **Как исправить:**
  В `config.yaml` выставить `default_deficit_kcal: 500` (стандартный физиологический дефицит).

### Дефект 9: Устаревшие алгоритмы в модуле консилиума (`council_data.py`)
* **Где:** [`health_core/council_data.py:90-97`](file:///opt/webapps/health_agent_system/health_core/council_data.py#L90)
* **Анализ:**
  Функция `_kcal_floor_now()` использует прямой вызов `adaptive_tdee()` или `bmr * factor`, минуя `daily_expenditure()` (блендер шагов и часов). В отчётах консилиума врачи видят одни цифры, а бот работает по другим.
* **Как исправить:**
  Унифицировать вызов через `daily_expenditure(conn, user_id, today)`.
