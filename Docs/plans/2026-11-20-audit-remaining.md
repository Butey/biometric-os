- Консоль Windows: запускать тесты с `PYTHONIOENCODING=utf-8`.
- Полный набор: `PYTHONIOENCODING=utf-8 python test_bot.py` и `PYTHONIOENCODING=utf-8 python -m bot.llm`. В test_bot.py на Windows ДО этих задач падают ровно 5 тестов (не регрессии): `knowledge_symlinks_cannot_expand_access`, `history_json_archive_preserves_originals_before_compaction`, `project_environment_shared_by_bot_and_admin`, `installer_moves_env_without_overwriting_secrets`, `review_foreign_identity_summary_is_rejected_and_not_loaded`. Всё остальное должно проходить.
- Не менять медицинские формулы, коэффициенты и политику в `health_core/energy.py` и `config.yaml` (`policy:`), не менять список провайдеров/моделей в `config.yaml`.
- Не трогать сервер, не перезапускать сервисы, не пушить.
- Тексты для человека - по-русски. В новых комментариях и строках - обычный дефис, не длинное тире.
- Простейшее рабочее решение, без лишних абстракций и опций сверх описанных.

## Task 1: Пустой ответ модели и «ключ не подходит к модели» (bot/llm.py)

Факты: 5 раз человеку ушло «Модель не подготовила ответ...», он слал сообщение заново. 23 раза провайдер отвечал `HTTP 503 ... This model is not available for this key`, а код ставил кулдаун 5 минут и снова пробовал.

1. В `run_loop`: финальный ответ без tool_calls с пустым или пробельным `content` - один автоматический повтор того же запроса (пустое assistant-сообщение из `messages` убрать перед повтором). Только если и повтор пустой - нынешний текст «Модель не подготовила ответ...». Повтор пустого ответа не тратит попытку поправки «записал без записи» и наоборот (отдельный флаг).
2. В `chat`: ответ провайдера с не-200 статусом, тело которого содержит `not available for this key` (без учёта регистра), обрабатывать как ошибку авторизации: кулдаун `_COOLDOWN_RATE_LIMIT_S`, запись в failures, переход к следующему ключу/провайдеру. Проверка до общей ветки «Прочие 4xx / 5xx».
3. Самопроверки в `if __name__ == "__main__"` файла bot/llm.py: (а) "" затем "ответ" -> текст "ответ", 2 запроса; (б) "" и "" -> текст-заглушка, 2 запроса; (в) 503 с телом `{"error": {"message": "This model is not available for this key."}}` -> у ключа кулдаун не меньше 3500 с от текущего момента. Существующий тест 7 (tool_call, затем пустой финал) поправить: добавить в очередь второй пустой ответ.

## Task 2: Лимит времени хода, промежуточное сообщение, дубль сообщения (bot/llm.py, bot/main.py, config.yaml, test_bot.py)

Факты: медиана ответа 17 с, 90-й процентиль 88 с, максимум 600 с. Человек повторял то же сообщение, пока бот молчал (07.11 обед три раза).

1. `run_loop(..., deadline_s: float | None = None)`: перед каждым вызовом `chat`, кроме самого первого, если с начала хода прошло больше `deadline_s` секунд (time.monotonic) - завершить ход так же, как при исчерпании `max_iters` (тот же текст «Не удалось завершить проверку данных...», `log.warning` с указанием дедлайна). Уже выполненные результаты инструментов остаются в возвращаемых messages.
2. `bot/main.py`: оба вызова `llm.run_loop` (текстовый ход и фото) передают `deadline_s=bot_cfg.get("turn_deadline_s", 120)`.
3. Промежуточное сообщение: в обоих местах вызова `run_loop` запустить задачу, которая через `bot_cfg.get("progress_note_s", 20)` секунд один раз отправляет человеку «Обрабатываю, ответ будет чуть позже.»; по завершении `run_loop` (в том числе с исключением) задача отменяется.
4. Дубль: если человек прислал текст, совпадающий (после strip и lower) с текстом хода, который для него сейчас ждёт или исполняется, бот отвечает «Это сообщение уже обрабатываю, дождись ответа.» и не ставит его в очередь. Реализация: словарь `uid -> нормализованный текст` хода в работе, заполняется до ожидания `_user_lock(uid)` в текстовой ветке `handle_message` и очищается в finally; проверка - чистая функция, её и тестировать.
5. В `config.yaml` в раздел `bot:` добавить `turn_deadline_s: 120` и `progress_note_s: 20`.
6. Тесты в test_bot.py: дедлайн (scripted-провайдер: первый ответ tool_call, `deadline_s=0` -> второго запроса нет, текст «Не удалось завершить», результат инструмента в messages) и проверка дубля (тот же текст в работе -> дубль; другой текст или другой uid -> не дубль).

## Task 3: Тренд веса после импорта весов (health_core/report.py, bot/main.py, test_bot.py)

Факты: человек 5 раз спрашивал «почему снова +1 кг», хотя с 15.10 по 20.11 вес снизился с 113.3 до 109.2 кг (около 0.8 кг/нед). Бот отвечал моделью, а не цифрами тренда.

1. В `health_core/report.py` функция `weight_trend_line(conn, user_id) -> str | None`:
   - дневное значение = медиана `body_metrics.weight_kg` за дату по замерам с 06:00 до 11:00 (как `_morning_weights` в energy.py);
   - сглаженный вес на дату D = среднее дневных значений в окне [D-6, D]; нужно не меньше 3 дней в окне, иначе нет значения;
   - L = последняя дата с утренним замером; S(L) - текущий сглаженный вес; если его нет - вернуть None;
   - для N из (14, 28): если есть S(L-N), изменение = S(L) - S(L-N), темп = изменение / N * 7;
   - строка: `Тренд веса (среднее за 7 дней): 109.4 кг; за 14 дн. -0.9 кг (-0.45 кг/нед); за 28 дн. -3.0 кг (-0.75 кг/нед). Дневные скачки до 1 кг - вода и соль, смотри на тренд.` Части за 14/28 дней без данных опускаются. Числа: вес с одним знаком, изменение с одним, темп с двумя, знак `+` для роста, `-` для снижения.
2. `bot/main.py`, `_handle_document`: после успешного импорта (`added > 0`) файла, который дал замеры веса (не тренировка: `act` пустой), дописать к `ans_text` строку тренда (через пустую строку), если функция вернула не None. user_id - тем же способом, что уже используется в этом обработчике. Ошибка расчёта тренда не должна ломать ответ об импорте (логировать и отвечать без тренда).
3. Тест в test_bot.py: засеять утренние веса на 30 дней с известным линейным снижением и шумом внутри дня, проверить числа в строке; дни только вечерних замеров не учитываются; меньше 3 дней - None.
