## 1. Архитектурный обзор подсистем

Архитектура системы разделена на два взаимосвязанных контура:
1. **Контур пакетного и файлового импорта (`health_core/ingest`)**:
   - Обеспечивает прием данных от физических приборов (напольные диагностические весы, спортивные часы, фитнес-браслеты) и текстовых дневников.
   - Главные архитектурные требования:
     - **Идемпотентность**: повторный запуск импорта того же файла или директории не должен искажать статистику, дублировать записи или затирать валидные исторические данные.
     - **Устойчивость к «ловушке нуля» (zero-trap)**: во внешних датчиках значение `0` почти всегда означает «замер не снят» (должно преобразовываться в SQL `NULL`), кроме специфических показателей (например, уровень висцерального жира `visceral_fat`, где 0 — допустимое минимальное значение).
     - **Кластеризация измерений (burst clustering)**: объединение серий повторных взвешиваний за короткий интервал времени в единую медианную точку с устойчивым суррогатным ключом `burst_key`.

2. **Интерфейсный контур агента (`plugin/tools.py` и `plugin/schemas.py`)**:
   - Связывает языковую модель (LLM в среде Hermes Gateway) и доменную логику `health_core`.
   - Регистрирует **30 инструментов** (`register_tool`) и **7 слэш-команд** (`register_command`).
   - Обеспечивает строгий контроль личности вызывающего (`_caller_telegram_id`, `_CALLER_FALLBACK`), исключая подделку Telegram ID.
   - Предотвращает прием галлюцинированных параметров от LLM (`_handler_wrapper`).
   - Выполняет валидацию временных меток событий на правдоподобность (`_norm_event_ts`), отсекая ошибочные года (2024/2025) или события из будущего.
   - Формирует текстовые визуализации (консольный пульт 34 символа, спарклайны трендов, журнал питания, дашборды).

## 2. Анализ модулей Ingest

### 2.1 `health_core/ingest/scale.py`

Модуль предназначен для импорта диагностических выгрузок весов Feelfit в таблицу `body_metrics`.

#### 2.1.1 Сигнатуры функций и докстринги
- `_sha256(path: str) -> str`: Вычисляет хеш SHA-256 файла блоками по 1 МБ (`1 << 20`).
- `_to_float(raw) -> float | None`: Преобразует строковые и числовые значения в `float`. Возвращает `None`, если входное значение `None`, пустая строка `""` или прочерк `"-"`. Заменяет запятые на точки. При ошибке `ValueError` возвращает `None`.
- `_read_rows(path: str) -> Generator[dict]`: Генератор. Отдает по строке сырых значений, ключи — канонические имена полей схемы. Если файл `.csv`, читает через `csv.reader(encoding="utf-8-sig")`. Для `.xlsx` и псевдо-`.xls` использует `openpyxl.load_workbook(fh, read_only=True, data_only=True)`.
- `_parse_row(raw: dict) -> dict | None`: Валидирует и очищает сырую строку. Парсит дату формата `%d/%m/%Y %H:%M:%S`. Отбрасывает строки без даты или веса. Заменяет `0` на `None` для всех полей, кроме `visceral_fat`.
- `_cluster_bursts(rows: list[dict], gap_sec: int) -> list[dict]`: Группирует замеры, следующие подряд с интервалом `<= gap_sec` (по умолчанию 120 с). Схлопывает кластер в одну запись: время первой точки серии как `burst_key` и `measured_at`, медиана (`statistics.median`) по каждому биометрическому полю, первый непустой `device_mac`.
- `import_export(conn, user_id: int, path: str) -> dict`: Главная функция импорта выгрузки весов. Возвращает `{"added": n, "skipped": n, "bursts": n}`.

#### 2.1.2 Алгоритмы и логика
1. **Маппинг колонок (`COLUMNS`)**:
   Словарь связывает исходные русские заголовки Feelfit с именами колонок БД. Опечатка разработчиков Feelfit `"Скелетные мыщцы(%)"` сохранена дословно, чтобы не ломать сопоставление. Поле `"Имя устройства"` игнорируется.
2. **Обход ограничения `openpyxl` на расширение файла**:
   Реальные экспорты приложения часто называются `*.xlsx.xls` (настоящий OOXML zip с двойным расширением). Если передать путь строкой, `openpyxl` проверяет расширение и падает с ошибкой неподдерживаемого формата. Модуль обходит это, передавая файловый объект `open(path, "rb")`, отключая внутреннюю проверку расширения в библиотеке.
3. **Ловушка нуля**:
   В диагностических весах при взвешивании без контакта с электродами процент жира, мышц, воды и BMR отдаются как `0`. В БД они должны попадать как `NULL`. Исключение — висцеральный жир (`visceral_fat`), где нулевой уровень возможен по шкале прибора.
4. **Кластеризация серий (`_cluster_bursts`)**:
   Замеры сортируются по `measured_at`. Если дельта между текущим и предыдущим закластеризованным замером `<= gap_sec`, он объединяется в серию. Это защищает от дрожания измерений и исключает пложение фиктивных точек в БД.

#### 2.1.3 SQL-запросы
```sql
-- Проверка повторного импорта по SHA-256
SELECT 1 FROM import_log WHERE file_hash=?;

-- Вставка серии взвешивания (динамический перечень колонок)
INSERT INTO body_metrics(user_id, burst_key, measured_at, weight_kg, fat_pct, bmi,
  skeletal_muscle_pct, muscle_mass_kg, protein_pct, device_bmr_kcal, ffm_kg,
  subcutaneous_fat_pct, visceral_fat, water_pct, bone_mass_kg, metabolic_age, device_mac)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
ON CONFLICT(user_id, burst_key) DO NOTHING;

-- Фиксация файла в журнале импорта
INSERT INTO import_log(user_id, imported_at, file_hash)
VALUES (?, ?, ?)
ON CONFLICT(file_hash) DO NOTHING;
```

#### 2.1.4 Обработка ошибок
- Подавление ошибок парсинга чисел в `_to_float` (`except ValueError: return None`).
- Подавление некорректных дат в `_parse_row` (`except ValueError: return None`).
- Очистка дескриптора книги `openpyxl` через `try ... finally: wb.close()`.
- Идемпотентный возврат нулей `{"added": 0, "skipped": 0, "bursts": 0}` при совпадении хеша файла.

#### 2.1.5 Константы и граничные условия
- `burst_gap_sec`: 120 секунд (конфигурируется в `config.yaml` в секции `ingest.burst_gap_sec`).
- Буфер чтения хеша: 1 МБ (`1 << 20`).
- Формат даты: жестко фиксирован `%d/%m/%Y %H:%M:%S`.

#### 2.1.6 Потенциальные проблемы
1. **Эффект бесконечной цепочки (Chaining effect)**: Если измерения проводятся каждые 110 секунд непрерывно, алгоритм объединит их в один гигантский кластер вместо разделения на сессии.
2. **Жесткая привязка к формату даты**: Если приложение весов сменит формат даты на ISO (`YYYY-MM-DD HH:MM:SS`) или локализованный американский `%m/%d/%Y`, строки будут молча отброшены (`_parse_row` вернет `None`).

### 2.2 `health_core/ingest/tcx.py`

Модуль предназначен для потокового импорта файлов тренировок TCX в таблицу `activity`.

#### 2.2.1 Сигнатуры функций и докстринги
- `_sha256(path: str) -> str`: Вычисляет SHA-256 файла порциями по 1 МБ.
- `_sport_from_filename(path: str) -> str | None`: Извлекает имя спорта из имени файла регулярным выражением `^\d{8}(.+?)(?:_\d+)?$`.
- `_parse_summary(path: str) -> dict`: Потоковый разбор XML через `ET.iterparse`, извлечение `started_at`, `duration_sec`, `kcal`, `avg_hr`.
- `import_tcx(conn, user_id: int, path: str) -> dict`: Главная точка импорта. Возвращает `{"added": 0|1, "skipped": 0|1}`.

#### 2.2.2 Алгоритмы и логика
1. **Потоковый разбор TCX**:
   Тренировочные файлы содержат сотни тысяч точек `<Trackpoint>`. Для БД нужны только суммарные метрики заезда/забега. Разбор реализован через `ET.iterparse(path, events=("start", "end"))` с немедленным вызовом `el.clear()`, что освобождает память от дочерних трекпоинтов и предотвращает рост потребления RAM.
2. **Определение вида спорта из имени файла**:
   Поскольку тег `<Activity Sport="...">` в экспортах трекеров часто пуст или содержит generic-имя, источником истины выступает имя файла (например, `20260820Ходьба_01.tcx` -> `Ходьба`).
3. **Хеширование и идемпотентность**:
   Таблица `activity` имеет ограничение уникальности `UNIQUE(file_hash)`.

#### 2.2.3 SQL-запросы
```sql
SELECT 1 FROM activity WHERE file_hash=?;

INSERT INTO activity(user_id, started_at, duration_min, kcal, avg_hr, sport, file_hash)
VALUES (?, ?, ?, ?, ?, ?, ?)
ON CONFLICT(file_hash) DO NOTHING;

INSERT INTO import_log(user_id, imported_at, file_hash)
VALUES (?, ?, ?)
ON CONFLICT(file_hash) DO UPDATE SET imported_at=excluded.imported_at;
```

#### 2.2.4 Критический баг и потенциальные проблемы
> [!WARNING]
> **Критический дефект парсинга тега `<Calories>`:**
> В функции `_parse_summary` (строки 36–48):
> ```python
> if event == "start":
>     if tag == "Lap":
>         in_lap = True
>     continue
> ...
> elif tag == "Calories" and not in_lap and kcal is None:
>     kcal = el.text
> ```
> Флаг `in_lap` становится `True` на старте узла `Lap`, но **никогда не сбрасывается в `False` на событии `end`**!
> В подавляющем большинстве TCX-файлов (Garmin, Polar, Wahoo, Strava) тег `<Calories>` находится **внутри** блока `<Lap>`. Так как `in_lap == True`, условие `not in_lap` ложно, и поле `kcal` никогда не считывается (всегда остается `None`).

Дополнительные проблемы:
- `datetime.strptime(summary["started_at"], "%Y-%m-%dT%H:%M:%S.%fZ")`: если время в TCX записано без долей секунд (например, `2026-08-20T10:00:00Z`), возникнет `ValueError`, и тренировка не загрузится.

### 2.3 `health_core/ingest/anthro.py`

Разбор текстовых замеров обхватов тела (талия, грудь, таз, бедро, шея, бицепс) и их сохранение в таблицу `anthropometry`.

#### 2.3.1 Сигнатуры функций и докстринги
- `_parse_value(raw) -> float`: Преобразует числовое значение или диапазон (`"113-114"`) к середине интервала `113.5`.
- `parse_text(text: str, default_year: int | None = None) -> list[dict]`: Построчный парсинг текста. Строка с датой открывает сессию замеров.
- `import_anthro(conn, user_id: int, records: list[dict]) -> dict`: Сохранение записей в БД с возвратом `{"added": n, "skipped": n}`.

#### 2.3.2 Алгоритмы и логика
- Фиксированный набор анатомических зон: `SITES = {"талия", "грудь", "таз", "бедро", "шея", "бицепс"}`.
- Строка даты вида `09.05` или `09.05.2026` открывает контекст даты. Если год отсутствует, берется год предыдущей даты либо `default_year` / текущий год.
- Все строки вида `<зона> <число>` связываются с текущей активной датой.
- Диапазоны вида `A-B` преобразуются в среднее арифметическое: `round((float(lo) + float(hi)) / 2, 2)`.

#### 2.3.3 SQL-запросы
```sql
INSERT INTO anthropometry(user_id, measured_on, site, value_cm)
VALUES (?, ?, ?, ?)
ON CONFLICT(user_id, measured_on, site) DO NOTHING;
```

#### 2.3.4 Обработка ошибок и проблемы
- `_DATE_RE = re.compile(r"^(\d{1,2})[.,](\d{1,2})(?:[.,](\d{4}))?$")`: даты в формате ISO (`2026-05-09`) не матчатся и пропускаются.
- Если строка содержит некорректное числовое значение, `_parse_value` выбрасывает необработанный `ValueError`, прерывая весь импорт.

### 2.4 `health_core/ingest/sleep.py`

Импорт суточных выгрузок сна браслета Xiaomi Band из markdown-файлов `Metrics/Sleep/**/sleep_statistics_YYYY-MM-DD.md`.

#### 2.4.1 Сигнатуры функций и докстринги
- `_minutes(text: str) -> int | None`: Перевод строки вида «8 ч 25 мин» в минуты (505). Если ни часов, ни минут нет — возвращает `None`.
- `_field(text: str, label: str) -> str | None`: Поиск значения по регулярке `\*\*label[^:*]*:\*\*\s*([^\n*]+)`.
- `_num(text: str, label: str) -> float | None`: Извлечение числа из текстового поля.
- `parse(path: Path) -> dict | None`: Парсинг одного markdown-файла выгрузки сна.
- `import_dir(conn: sqlite3.Connection, user_id: int, root: Path | None = None) -> dict`: Пакетный UPSERT всех файлов директории.

#### 2.4.2 Алгоритмы и логика
- **Источник даты ночи**: Дата ночи извлекается строго из **имени файла** (`\d{4}-\d{2}-\d{2}`), а не из русского текста заголовка («от 21 мая 2026 г.»), исключая ошибки локализации месяцев.
- **Раздельный поиск компонентов времени в `_minutes`**: Поиск часов (`_H_RE`) и минут (`_M_RE`) выполняется отдельными регулярными выражениями, что предотвращает ложное срабатывание на пустую строку.
- **Интеллектуальный UPSERT**: Сохраняет существующие ручные правки полей в БД (`bedtime`, `wake_time`, фазы, пульс, SpO2) через `COALESCE(excluded.field, field)`. Длительность `duration_min` обновляется безусловно.

#### 2.4.3 SQL-запросы
```sql
INSERT INTO sleep_log(user_id, night_date, bedtime, wake_time, duration_min,
  deep_min, rem_min, efficiency_pct, hr_avg, spo2_avg, source)
VALUES (?,?,?,?,?,?,?,?,?,?,?)
ON CONFLICT(user_id, night_date) DO UPDATE SET
  bedtime=COALESCE(excluded.bedtime, bedtime),
  wake_time=COALESCE(excluded.wake_time, wake_time),
  duration_min=excluded.duration_min,
  deep_min=COALESCE(excluded.deep_min, deep_min),
  rem_min=COALESCE(excluded.rem_min, rem_min),
  efficiency_pct=COALESCE(excluded.efficiency_pct, efficiency_pct),
  hr_avg=COALESCE(excluded.hr_avg, hr_avg),
  spo2_avg=COALESCE(excluded.spo2_avg, spo2_avg),
  source=COALESCE(excluded.source, source);
```

#### 2.4.4 Потенциальные проблемы
- Хрупкость парсинга фаз сна: регулярка `\*\*{name}\*\*[^|]*\|[^|]*\|([^|]*)\|` жестко привязана к колонкам markdown-таблицы. Смена порядка колонок в приложении браслета сломает сбор фаз глубокого и быстрого сна.

### 2.5 `health_core/ingest/diary.py`

Импорт рукописных markdown-дневников питания и воды из директории `Nutrition/YYYY-MM-DD.md`.

#### 2.5.1 Сигнатуры функций и докстринги
- `_clean(cell: str) -> str`: Очистка markdown-разметки и экранирования.
- `_num(cell: str) -> float | None`: Извлечение вещественного числа из ячейки.
- `_grams(cell: str) -> float | None`: Извлечение граммовки. Приоритет отдается значению в скобках `(~215 г)` перед штуками `3 шт.`.
- `parse(path: Path) -> dict | None`: Разбор структуры файла дневника на приемы пищи, блюда и воду.
- `import_dir(conn: sqlite3.Connection, user_id: int, root: Path | None = None) -> dict`: Импорт каталога с предварительным удалением старых записей за день.

#### 2.5.2 Алгоритмы и логика
- Сопоставление заголовков приемов пищи: `_MEAL_RE` матчит `### Завтрак (08:30)`. Слот определяется по вхождению ключевых слов (`завтрак` -> `breakfast`, `обед` -> `lunch`, `ужин` -> `dinner`, иначе `snack`).
- Фильтрация ложных позиций: игнорируются строки таблицы с названиями `Продукт`, `:-`, содержащие подстроку `ИТОГО` (защита от удвоения калорий) или `вода` (защита от дублирования гидратации).
- Учет воды: строки вида `**10:00** - 500 мл` парсятся регуляркой `_WATER_RE`.
- **Стратегия перезаписи дня**: При импорте дневника выполняется предварительное удаление всех записей за эту дату:
  `DELETE FROM food_log WHERE user_id=? AND date(eaten_at)=?`.

#### 2.5.3 SQL-запросы
```sql
DELETE FROM food_log WHERE user_id=? AND date(eaten_at)=?;
INSERT INTO food_log(user_id, eaten_at, meal_slot) VALUES (?,?,?);
INSERT INTO food_items(food_log_id, name, grams, kcal, protein_g, fat_g, carbs_g) VALUES (?,?,?,?,?,?,?);

DELETE FROM water_log WHERE user_id=? AND date(at)=?;
INSERT INTO water_log(user_id, at, volume_ml) VALUES (?,?,?);
```

#### 2.5.4 Потенциальные проблемы
> [!CAUTION]
> **Каскадное удаление и потеря оперативных логов:**
> 1. Если в соединении с SQLite не выполнена команда `PRAGMA foreign_keys = ON;`, удаление строки `food_log` **не удалит** связанные записи в `food_items`. Это приведет к накоплению записей-сирот в БД при каждом повторном импорте!
> 2. Импорт файла дневника полностью затирает все блюда, которые пользователь логировал через телеграм-бота в течение дня.

## 3. Спецификации инструментов: `plugin/schemas.py`

Файл содержит спецификации всех 30 инструментов системы в стандарте JSON Schema Draft-07.

### Сводная таблица параметров и ограничений инструментов

| Инструмент | Обязательные поля | Допустимые действия (`action`) / Ограничения | Назначение |

## 4. Глубокий анализ `plugin/tools.py`

### 4.1 Архитектурные паттерны и механизмы безопасности

1. **Изоляция звонящего через `ContextVar` (`_CALLER_FALLBACK`)**:
   В асинхронном шлюзе Hermes сообщения от разных Telegram-пользователей обрабатываются в параллельных корутинах. Хук `pre_gateway_dispatch` сохраняет `event.user_id` в `ContextVar[str | None]`, исключая утечку идентичности между сессиями.
2. **Перехват быстрых макросов (`_quick_macro_rewrite`)**:
   Пользовательские сообщения вида `+30 белка`, `+500 мл`, `+1.5 л воды` перехватываются регулярным выражением `_QUICK_MACRO_RE` и переписываются в явную модельную инструкцию. Это позволяет фиксировать воду и добор макросов без уточняющих диалогов.
3. **Безопасное определение прав и пользователя (`_caller_telegram_id`, `_get_user_id`)**:
   `_caller_telegram_id()` считывает `HERMES_SESSION_USER_ID` из контекста сессии, либо запасной ContextVar. Функция `_get_user_id` разрешает Telegram ID в целочисленный `users.id` через запрос к базе данных. Если переданный Telegram ID отсутствует в БД, генерируется исключение (принцип fail-closed).
4. **Защита от галлюцинаций LLM через `_handler_wrapper`**:
   Декоратор автоматически инспектирует параметры по соответствующей схеме `schemas.<name>_schema`. Если модель присылает неизвестный аргумент, инструмент немедленно возвращает JSON с ошибкой `Неизвестные параметры: ...`.
5. **Контроль правдоподобия времени (`_norm_event_ts`)**:
   Функция проверяет дату произошедших событий (еда, вода, замеры). Запрещает даты старше 400 дней в прошлом и более чем на 2 дня в будущем.
6. **Защита целостности числовых колонок (`_as_float`)**:
   Предотвращает запись строкового мусора в столбцы типа REAL базы SQLite, отлавливая некорректные типы до выполнения `INSERT`.

### 4.2 Детальный разбор 30 хендлеров инструментов

#### 1. `handle_log_food`
- **Логика**:
  - `action == "delete"`: вызывает `_delete_food`. Проверяет принадлежность записи пользователю (`user_id`). Удаляет блюда по подстроке имени или прием целиком. Если в приеме не осталось блюд, удаляет родительскую запись `food_log`.
  - `action == "add"`:
    - Проверяет непустой массив `items`.
    - Проверяет `meal_slot` строго по множеству `{"breakfast", "lunch", "dinner", "snack"}`.
    - Требует обязательного наличия `kcal`, `protein_g`, `fat_g`, `carbs_g` для каждой позиции.
    - Ограничивает калорийность отдельной позиции потолком `_max_item_kcal()` (1200 ккал), блокируя попытку модели записать дневной рацион одной строкой.
    - Проверяет число фактически созданных записей `_written == len(items)`. При несовпадении выполняет `conn.rollback()` и удаляет прием.
    - Запускает проверку гардрейлов безопасности `check_all` и сохраняет алерты в `alerts`.
    - Возвращает обновленный статус-бар.

#### 2. `handle_log_water`
- **Логика**:
  - `action == "list"`: отдает список записей за дату с объемами и суммарный итог дня.
  - `action == "delete"`: удаляет конкретную запись по `water_id`, либо последнюю запись дня, либо все записи дня при `clear_day=True`.
  - `action == "add"`: валидирует объем `ml > 0`. Запрещает ноль и отрицательные объемы. Вставляет запись в `water_log`, проверяет гардрейлы и возвращает прогресс по суточной норме воды.

#### 3. `handle_log_sleep`
- **Логика**:
  - `action == "delete"`: удаляет запись по `sleep_id` с проверкой владельца.
  - `action == "add"`:
    - Дата ночи валидируется по формату `YYYY-MM-DD`.
    - Длительность сна `duration_min` проверяется в диапазоне `1..1440` мин.
    - Субъективная оценка `quality` проверяется в диапазоне `1..5`.
    - Фазы (`deep_min`, `rem_min`, `awake_min`) проверяются на вхождение в интервал `0..duration_min`.
    - Выполняет UPSERT в `sleep_log` по `(user_id, night_date)`.
    - Возвращает среднюю длительность сна за последние 7 дней.

#### 4. `handle_log_glucose`
- **Логика**:
  - `action == "delete"`: удаление замера сахара по `glucose_id`.
  - `action == "add"`: валидирует `mmol_l` через `_as_float`. Вычисляет мгновенный тренд по разнице с предыдущим замером. Проверяет гардрейлы сахара.

#### 5. `handle_log_weight`
- **Логика**:
  - `action == "delete"`: удаление взвешивания по `weight_id`.
  - `action == "add"`:
    - Валидирует `weight_kg` и поля биоимпеданса через `_as_float`.
    - Формирует `burst_key` из таймстемпа замера.
    - Вычисляет дельту к предыдущему замеру веса.
    - Вставляет данные в `body_metrics` с защитой от дублирования `ON CONFLICT(user_id, burst_key) DO NOTHING`.
    - Вызывает `mark_achieved_milestones`: проверяет достижение целевых вех по весу, сухой массе или проценту жира. Достигнутые вехи помечаются и возвращаются для однократного анонса.

#### 6. `handle_log_anthropometry`
- **Логика**:
  - `action == "delete"`: удаление замера по `anthropometry_id`.
  - `action == "add"`:
    - Проверяет зону `site` строго по `_ANTHRO_SITES` (`талия`, `грудь`, `таз`, `бедро`, `шея`, `бицепс`).
    - Валидирует `value_cm` через `_as_float`.
    - Находит предыдущий замер этой зоны и вычисляет дельту.
    - При замере талии проверяет и закрывает вехи типа `waist`.

#### 7. `handle_log_med`
- **Логика**:
  - `action == "delete"`: удаление записи приема препарата по `med_id`.
  - `action == "add"`:
    - Канонизирует название через `_canon_med` (синонимы и торговые марки сводятся к единому стандарту).
    - Валидирует путь введения `route` строго по `{"injection", "oral", "topical"}`.
    - Валидирует единицу дозы `unit` по `{"mg", "ml", "IU", "mcg"}`.
    - Сохраняет прием в `med_log`.
    - **Учет остатков и сдвиг графика**: если в `med_schedule` есть курс по этому препарату, уменьшает `stock_doses` на 1 и сдвигает дату следующего приема `next_at` на `every_days`.

#### 8. `handle_log_workout`
- **Логика**:
  - `action == "list"`: отдает последние N тренировок из `activity`.
  - `action == "delete"`: удаляет запись по `workout_id` и связанный хеш из `import_log`.
  - `action == "add"`: валидирует `duration_min > 0`, `kcal >= 0`, `avg_hr > 0`. Создает синтетический SHA-256 хеш `manual_{user_id}_{started_at}_{sport}_{duration}` для обеспечения уникальности и сохраняет в `activity`.

#### 9. `handle_import_scale_export`
- **Логика**:
  - Проверяет обязательный путь `file_path`.
  - При наличии префикса `gdrive:` скачивает файл во временную директорию через `rclone_pull`.
  - Ограничивает размер файла лимитом 20 МБ (`_MAX_IMPORT_BYTES`).
  - Определяет реальный формат файла по первым байтам (`_sniff_import_format`).
  - Если расширение расходится с содержимым, переименовывает во временный файл с правильным суффиксом.
  - Делегирует разбор в `scale.import_export` или `tcx.import_tcx`.
  - Очищает временные файлы и возвращает счетчики `added`, `skipped`, `bursts`.

#### 10. `handle_get_day_summary`
- **Логика**:
  - Нормализует дату. Автоматически пересчитывает цели дня через `daily_target(conn, user_id, date_str)`.
  - Поддерживает 4 формата вывода:
    - `dashboard`: полный markdown-отчет с прогресс-барами КБЖУ, воды, баланса тарелки и алертов.
    - `journal`: разбивка съеденного по приемам пищи с ID для удаления (`#N`) и строкой метрик тела `_metrics_line`.
    - `console`: узкий 34-символьный блок в моноширинном формате для экрана смартфона.
    - `bar`: сырой JSON-объект.

#### 11. `handle_get_trends`
- **Логика**: Читает тренды веса, сухой массы, талии и расчетного расхода TDEE за `window_days` через `report.trends`. Добавляет статистику эффективности тренировок из TCX через `training_efficiency`.

#### 12. `handle_get_status_bar`
- **Логика**:
  - Возвращает компактную строку статуса `status_bar` либо дашборд при `format="dashboard"`.
  - Извлекает активный стиль персоны (`_active_style`) и передает его в отдельном поле `style`. Это обеспечивает инъекцию стиля ответов в контекст диалога с пользователем.

#### 13. `handle_get_evening_report`
- **Логика**: Формирует вечерний аналитический отчет за дату через `evening_report`.

#### 14. `handle_help`
- **Логика**: Возвращает статическую инструкцию `_HELP_USER`. Если текущий режим пользователя `admin`, дописывает команды администрирования `_HELP_ADMIN`.

#### 15. `handle_get_weekly_summary`
- **Логика**: Генерирует недельный отчет через `weekly_summary`. Читает ранее зафиксированные алерты из таблицы `alerts` без повторного вызова `check_all` (предотвращая нарушение правила «один алерт в сутки»).

#### 16. `handle_query_metrics`
- **Логика**: Защищает от SQL-инъекций путем жесткого сопоставления имени метрики с физической колонкой БД через словарь `_METRIC_MAP`. Выбирает временной ряд за `window_days`.

#### 17. `handle_query_food`
- **Логика**: Извлекает блюда за диапазон дат через соединение `food_log` и `food_items`.

#### 18. `handle_pantry`
- **Логика**:
  - `action == "list"`: группирует продукты по категориям (`Белковые`, `Молочка/Сыры`, `Овощи/Фрукты` и т.д.).
  - `action == "add"`: при повторном добавлении суммирует количество `qty` с существующим остатком.
  - `action == "remove"`: уменьшает количество либо полностью удаляет продукт, если остаток исчерпан.

#### 19. `handle_equipment`
- **Логика**:
  - `action == "list"`: возвращает перечень доступного инвентаря.
  - `action == "add"`: выполняет UPSERT инвентаря по `(user_id, name)`.
  - `action == "remove"`: удаляет инвентарь по имени.

#### 20. `handle_plan_day`
- **Логика**:
  - `action == "list"`: возвращает превью ранее сохраненных планов питания/тренировок.
  - `action == "get"`: возвращает детальный текст плана на дату.
  - `action == "save"`: сохраняет план. **Барьер**: запрещает сохранение плана тренировки, если в `equipment` нет ни одной единицы инвентаря.
  - `action == "delete"`: удаляет план на дату или все планы выбранного типа.

#### 21. `handle_forecast`
- **Логика**:
  - `action == "project"`: формирует прогноз массы на горизонт до 182 дней по модели энергетического баланса Холла с учетом метаболической адаптации.
  - `action == "reach"`: вычисляет дату и количество дней до достижения целевого веса `target_kg`.

#### 22. `handle_refeed`
- **Логика**: Управляет циклом рефидов по протоколу MATADOR. `action=status` показывает текущую фазу (дефицит/поддержание), `schedule` формирует график 2/2 недели, `clear` отменяет будущие фазы.

#### 23. `handle_style`
- **Логика**:
  - `action == "list"`: выводит стили общения агента.
  - `action == "add"`: сохраняет новый стиль.
  - `action == "use"`: делает стиль активным (в транзакции сбрасывает флаг у всех и ставит выбранному).
  - `action == "del"`: удаляет стиль. **Защита**: запрещено удалять стиль `debian` и текущий активный стиль; требует подтверждения `confirm: "УДАЛИТЬ"`.

#### 24. `handle_explain_target`
- **Логика**: Возвращает строку `computed_from` из `daily_targets`, расшифровывающую шаг за шагом формулу калорийности на дату.

#### 25. `handle_get_progress`
- **Логика**: Находит веху по имени, извлекает актуальное значение метрики из соответствующей таблицы (`body_metrics` или `anthropometry`) и вычисляет оставшийся путь до цели.

#### 26. `handle_register_user`
- **Логика**:
  - Идентичность берется строго из `_caller_telegram_id()`.
  - Требует обязательного заполнения `height_cm`, `birth_date`, `sex` (необходимы для BMR).
  - Выполняет UPSERT пользователя в таблице `users`.
  - Автоматически рассчитывает и инициализирует базовые цели в `user_targets` через `config.targets_for()`.

#### 27. `handle_set_milestone`
- **Логика**: Проверяет метрику по белому списку `["weight_kg", "ffm_kg", "fat_pct", "waist"]`. Выполняет UPSERT вехи по `(user_id, name)`.

#### 28. `handle_admin_cmd`
- **Логика**:
  - Проверяет аутентификацию звонящего (fail-closed при отсутствии ID).
  - Проверяет вхождение в список `telegram_admin_ids` конфигурационного файла.
  - Подкоманды администрирования:
    - `mode [user|admin]`: переключение режима администрирования.
    - `status`: статистика по пользователям и строкам таблиц.
    - `guards`: статус всех 14 гардрейлов безопасности.
    - `targets`: вывод порогов из `config.yaml`.
    - `set <key> <val>`: построчное безопасное обновление `config.yaml` с сохранением комментариев, валидацией синтаксиса и созданием резервной копии `.bak`.
    - `milestone add/del`, `milestones`: управление вехами.
    - `recalc [date]`: принудительный перерасчет целевых калорий.
    - `export`, `backup`: запуск экспорта и резервного копирования БД.
    - `alerts [N]`: просмотр последних N алертов.

### 4.3 Слэш-команды Hermes

Слэш-команды вызываются напрямую в чате Telegram и возвращают форматированный текст:
1. `cmd_health`: вызов справки системы (`/health`).
2. `cmd_style`: управление стилями ответов (`/style list|use|add|del`).
3. `cmd_mode`: переключение режима пользователя/администратора (`/mode user|admin`).
4. `cmd_users`: список зарегистрированных персон и объем их данных (доступно только админу через `_admin_denial`).
5. `cmd_wipe`: очистка пользовательских логов в 12 таблицах (`food_log`, `water_log`, `glucose_log`, `body_metrics`, `anthropometry`, `activity`, `med_log`, `alerts`, `daily_targets`, `import_log`, `llm_calls`, `refeed_days`) с обязательным подтверждением `/wipe УДАЛИТЬ`. Профиль, вехи, инвентарь и стили сохраняются.
6. `cmd_week`: быстрый вывод недельной сводки (`/week`).
7. `cmd_importdata`: вызов импорта файла с локального диска сервера или Google Drive (`/importdata <путь>`).

### 4.4 Анализ дублирования логики

1. **Инициализация БД и миграций**:
   В начале каждого хендлера повторяется триплет:
   ```python
   conn = connect()
   migrate(conn)
   user_id = _get_user_id(params, conn)
   ```
   Вызов `migrate(conn)` при каждом вызове инструмента создает избыточные дисковые блокировки SQLite.
2. **Проверка гардрейлов**:
   В хендлерах `handle_log_food`, `handle_log_water`, `handle_log_glucose`, `handle_log_weight`, `handle_log_anthropometry`, `handle_log_med`, `handle_log_workout` блок проверки гардрейлов идентичен:
   ```python
   alerts = check_all(conn, user_id)
   record(conn, user_id, alerts)
   ```
3. **Удаление записей (`action == "delete"`)**:
   Во всех инструментах логирования процедура удаления (парсинг ID, `SELECT` с проверкой `user_id`, `DELETE`, `commit`, возврат JSON) дублирует один и тот же шаблон.

## 5. Сводная матрица проблем, граничных случаев и багов

| Компонент | Строки | Категория | Описание проблемы |
|---|---|---|---|
| `tcx.py` | 36–48 | **Критический БАГ** | Флаг `in_lap` устанавливается в `True` на теге `<Lap>`, но никогда не сбрасывается в `False`. Тег `<Calories>` внутри `<Lap>` игнорируется, калории тренировки теряются. |
| `tcx.py` | 68–70 | **Ошибка времени** | `strptime` падает с `ValueError`, если timestamp TCX не имеет миллисекунд (`.000Z`) или имеет таймзону отличную от `Z`. |
| `diary.py` | 86–105 | **Потеря данных** | `DELETE FROM food_log WHERE date(eaten_at)=?` стирает записи еды, введенные пользователем через Telegram-бота в течение дня. |
| `diary.py` | 86–96 | **Осиротевшие строки** | Если в SQLite не включен `PRAGMA foreign_keys = ON;`, удаление `food_log` не удаляет связанные строки `food_items`. |
| `scale.py` | 120–127 | **Логика кластеризации** | Chaining-эффект: непрерывная серия замеров с интервалом менее 120 сек схлопывается в один кластер независимо от общей длительности. |
| `anthro.py` | 9, 36–41 | **Валидация даты** | Регулярка даты не поддерживает стандартный ISO-формат `YYYY-MM-DD`. |
| `tools.py` | 3853–3866 | **Безопасность данных** | В подкоманде `_admin_milestone_del` удаление вехи выполняется только по `name` без проверки `user_id`, что может удалить чужую веху. |
| `tools.py` | Везде | **Производительность** | Многократный вызов `migrate(conn)` при каждом вызове любого инструмента создает паразитную нагрузку на файловую систему. |
